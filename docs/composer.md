## 1. なぜ作るか

### 文節 UI は解空間の損失のある射影になっている

Mozc（を含む現代のかな漢字変換）は、入力文字列に対してラティスを組み、
**単語の選択と区切りの決定を一つの最小コスト経路問題として同時に解いている**。
ありうる区切り方は最初から全部ラティスの中に同居していて、経路探索で一本に絞られる。
文節境界は `Segmenter`（品詞IDペアのビット配列）が経路の品詞列から規則的に導くだけで、
独立に選ばれているわけではない。

ところが UI は、この一つの同時選択を「境界を動かす」「候補を選ぶ」という
二つの逐次的な局所選択に因数分解している。この因数分解には正当な理由がある
（5文節×3候補＝243通りの経路に、5回の局所選択で到達できる。相互作用空間の指数的圧縮）。
しかし損失もある。

**1位経路と2位経路が区切りで食い違っているとき、候補ポップアップは原理的に無力**である。
いくら候補を選んでも直らない。ユーザーは「これは候補の問題ではなく区切りの問題だ」と
自分で診断してから、別の操作（境界の伸縮）に切り替える必要がある。
その診断のコストがユーザーに押し付けられている。

### 制約はエンジンではなくプロトコルにある

この制約は変換エンジンの限界ではない。`immutable_converter` は N-best 経路を既に計算しており、
区切りの違う候補は**エンジンの中に存在している**。出せないのはプロトコルの形式のせいである。

Mozc のプロトコル定義（`protocol/commands.proto`, `protocol/candidate_window.proto`）では、

- `Preedit.Segment` … 文節が `UNDERLINE` / `HIGHLIGHT` 付きでワイヤに乗り、**アプリ側が描画する**
- `CandidateWindow.Candidate` … 候補は `value`（文字列）＋ `index` のみ。
  候補ウィンドウは `position`（合成文字列内の文字位置）に紐づく

つまり**候補は「合成文字列のある位置を置き換える文字列」としてしか表現できない**。
区切りを変える候補はこのフォーマットに乗らない。IME 単体で変えられる話ではなく、
プロトコルとそれを描画する全アプリケーションの問題になる。

これは歴史的な経緯でもある。初期のかな漢字変換は**単文節変換**で、区切るのはユーザーの仕事だった。
文節ごとの候補リストは、その時代には完全に正しい設計である。その後、連文節変換で機械が境界を
推定するようになったが、UI とプロトコルは残った。

### hechima はプロトコルの外にいる

hechima は入力・キーマップ・変換・表示の 4 つの箱をページの中に持っている。
**preedit も候補ウィンドウも OS に渡さない**ので、この制約は構造的に存在しない。
ホストに渡すのは確定済みの文字列だけでよい。

**エンジンはもう答えを持っていて、出す道がないだけ**という状況なので、
道を作れば区切り違いの並列提案が成立する。

## 2. UI 仕様

### 2.1 全体の形

**エディタの本文の中に直接描く。オーバーレイは持たない。**
標準 IME の未確定表示（composition）と同じ枠組みで、打っているものがその場に現れる。

```
エディタ本文 ──────────────────────────────────────────────────
  会議は来週に延びた。 今日は雨だ。 昨日は晴れだった。 でもきょうはあめ▍
  ^^^^^^^^^^^^^^^^^^  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~  ------------
  確定（ホストのもの）  未確定（漢字かな交じり・マーク可）  打鍵中（ひらがな）
```

打ち進むと、**句点のたびにその文だけ**が漢字かな交じりに変わる。
変わっただけで、まだホストのものにはなっていない。
4 文目に入ると、いちばん古い文が確定してホストへ渡り、見た目が通常の本文に戻る。
以降その文はこのアプリの管轄外で、直したければエディタで普通に直す。

見た目は三つだけである。

| 状態 | 見た目 | 中身 |
|---|---|---|
| **打鍵中の文** | 破線下線（IME の未確定と同じ） | ひらがな。変換しない |
| **未確定の文**（最大 2 文） | 別の下線 ＋ マーク | 漢字かな交じり |
| **確定した文** | 通常の本文 | ホストのもの |

**位置の問題が消える。** テキストは常にキャレットのある場所にあり、
本文を覆うものも、追従させるものも無い。旧案の矩形オーバーレイとその配置（案 A / 案 B）、
矩形の寸法、隠す操作は、まとめて不要になった（経緯と、そこで測ったものの行き先は §2.8）。

### 2.2 三層モデル（場所ではなく状態）

| 層 | 中身 | 変換 | 書き換え | マーク |
|---|---|---|---|---|
| **打鍵中の文** | ひらがな | **しない** | – | **誤打のみ** |
| **未確定の文** | 変換済み | **句点で 1 回** | **しない** | **変換の不確実性** |
| **確定した文** | 変換済み | 済 | – | – |

この三層が設計の中核である。**分けているのは場所ではなく状態だった。**
旧案の矩形は三層を「三つの場所」として実装したもので、インラインに移しても三層は保たれる。

**打鍵中の文を変換しないことが、打鍵フィードバックのセーフガードになっている。**
ユーザーは常に誤打を意識しており、直近数文字が正しく打てているかを気にしている。
キャレット直近で自動変換が起きるとそのフィードバックが死ぬ。
打鍵中の文がひらがな専用である限り、キャレット直近は**構造的に必ず生ひらがな**になる。
「そんな直近では確定度が出ないから大丈夫」という確率的な期待に頼らず、設計として保証する。

**この保証は旧案より強くなった。** 旧案の 1行欄は末尾 40 かなの窓だったので、
長い文では先頭が既に変換されて矩形へ出ていた。インライン模型では**文まるごと**が生ひらがなである。

**ライブ変換を持たない。** 旧案の「現在の文」は打鍵のたびに変換し直して書き換わる層だった。
インライン模型にこの層は無く、変換は句点で 1 回だけ走る。

これは §2.4(b) の裏付けを**方針から構造へ**格上げする。旧稿は「現在の文にはマークを出さない
——書き換わる最中のものにマークを付けても視覚ノイズにしかならない」と方針で決めていたが、
いまは打鍵中の文が変換されていないので、**マークの対象そのものが存在しない**。

失うのは「先頭から漢字になっていくのが見える」体験である。§4.6 の実測では文長の中央値は
23〜31 字なので、**大半の文はひらがなのまま打ち切る**ことになる。

**未確定の文は書き換えず、マークで伝える。**
後から「1文目のあれは違うかもしれない」と分かっても、自動修正はしない。
表示は安定したまま、情報は失われず、直すかどうかはユーザーが決める。

**補足（2026-09-21・実地）: 「直近数文字」という論拠は弱まった。**
旧案の器を打ってみたところ、**誤打は直近だけでなく文の先頭にも出る**という報告が出た。
「ユーザーが気にしているのは直近数文字」の部分は、実地では成り立たない。

**ただし結論は変わらない。** キャレット直近が構造的に生ひらがなであることの価値は、
誤打がどこにあるかとは独立だからである。弱まったのは論拠であって設計ではない。
位置に依らない検出は §2.4(a) の誤打マークが担う —— つまりこの報告は、
**誤打マークを「あとで足す装飾」ではなく器の一部として扱え**という指摘として読むのが正しい。
インライン模型では文まるごとが生ひらがななので、誤打マークの守備範囲もそのまま文全体になる。

### 2.3 テキストの流れ

```
打鍵 → その場にひらがなで現れる（破線下線）
     → 句点を打つと、その文だけが漢字かな交じりに変わる（未確定のまま）
     → アプリが持つのは最大 3 文（打鍵中 1 ＋ 変換済み未確定 2）
     → 4 文目を打ち始めると最古の文が確定してホストへ渡る（FIFO）
```

**変換のトリガーは「区切りの合図」であって、句点という文字ではない**（2026-09-22 に言い換え）。
句点はその合図を**兼ねている最も自然な文字**にすぎない。合図だけを送る手段も要る（後述）。

**合図を受けたら、その場で即座に変換する。** 旧案は「句点ではなく次の文の1文字目」と決めていた。
**この模型では逆になる。判断の基準は同じで、結論だけが反転する。**

旧案の基準は「句点で即座に流すと、直前に打った数文字がフィードバックを受ける時間がゼロになる」
だった。旧案の「流す」は 1行欄からテキストが消えることだったので、1 文字ずらす猶予に意味があった。

インライン模型で句点が起こすのは**その場での変換**である。文字数が減ってキャレットが左へ飛ぶ。
これは受け入れる —— **句点はユーザーの中で一区切りが付く瞬間**であり、手が止まっている場所だからである。
1 文字ずらすと、**次の文を打ち始めた瞬間に**キャレットが飛ぶことになり、かえって悪い。
どちらも「ユーザーの注意がどこにあるか」で決めていて、注意の在りかが模型で違う。

**実地で確認した（2026-09-22。4a'' を実機で試した）。** 懸念していた飛距離は問題にならず、
理由まで付いた —— **標準 IME で散々経験している挙動だから**である。
確定時に文字数が変わってキャレットが動くのは IME では日常で、寄せ先を IME にした（§8.7）
ことの副産物として、この違和感も一緒に消えていた。

#### 「文を区切る」役 — 文字を伴わない合図（2026-09-22 決定）

句点を打たない入力（チャット・検索窓・見出し）では合図が来ない。
**句点を打ってから BS で消す**のも、**別の IME に切り替える**のも作業として不合理なので、
**句点と同じ働きをするが文字を産まない役**を用意する。

| | 既定 |
|---|---|
| JIS | **変換キー**（`Convert`） |
| US（変換キーが無い） | **修飾キー単押し**（右 Alt 等） |
| 共通 | **役として持ち、配列ごとに割り当て直せる**（keymap v2 の作法） |

**変換キーを既定にするのがいちばん筋が通る。** 文字を産まない、名前がそのもの、
IME 使用者の既存の反射がそのまま使える。**Space を空白に戻した代わりに、変換は変換キーがやる**
という形になり、§8.7 の「元に戻っただけ」が一段深くなる。

**副産物: 句点を打たない用途では、古典的な IME の三段がそのまま戻ってくる。**

```
けんさくご →[変換]→ 検索語 →[Enter]→ 確定
```

穴を塞ぐというより、**穴の底に標準 IME が敷いてあった**という形である。

**カーソル下（↓）は採らない。** IME で合成中の ↓ は「候補窓を開く / 次候補」なので、
同じキーに「区切る」を当てると反射が食い違う。さらに §2.4 で ←→ をマーク走査に使うため
矢印の語彙が三つになり、エディタの行移動も食う。この設計は未確定を 3 文持つので、
**普通の IME より矢印を長く握り続ける**ことになるのが効く。

**ホスト側で選択があるときの変換キーは再変換**（`reconvert`）に振る。IME の作法どおりで、
`site/src/app.ts` が既に `e.code === "Convert"` をそう扱っている。区切る役と衝突しない。

#### 残る代償: 句点を打たない用途こそ Space の反射が痛い

穴は塞がったが、**代償の置き場所が変わっただけ**でもある。

長文では句点が勝手に変換するので Space を押す必要が無い。ところが短文では明示的に
変換キーを押すことになり、そこで「Space = 変換」の反射が出る。しかも §2.6 のとおり
Space は空振りせず**空白を入れる**ので、押してしまうと**読みに空白が混ざる**。

**ここは Space 2 連打（§2.6）で受け止める。** 反射で押した空白は、もう一度押した時点で
消えて区切りに変わるので、**読みに残らない。** 長文では無害だった「空振りしないこと」が
短文では逆に働く、という問題は、この一段で塞がっている。

残るのは「一度も二度目を押さなかった人」だけで、その人は Enter でひらがなを流す
（§2.3 の Enter 二段目）。**どの道を通っても壊れない**のが、この三つの役の噛み合い方である。
実際にそう振る舞うかは §4.4b の「用途による差」で見る。

#### 後から変わるのはマークであって表記ではない

3 文を手元に置くが、**後続の文が前の文の変換をやり直すことはない。**
§5 のとおり Mozc の変換単位は実質 1 文で、文をまたぐ文脈は精度に使えない（空席のまま）。
文書内の一貫性（§8.1）は後から効くが、§2.4 のとおり**マークにのみ**使い、書き換えには使わない。

では未確定で持つ意味は何か。**経路を切り替えるのが 1 打鍵で済む猶予**である。
確定後も再変換（`reconvert`）で直せるが、選択してから開き直す手間が入る。
§5 の (b) ユーザーが 3 文を見渡して校正できる / (c) FIFO を滑らかに回す、がそのまま根拠になり、
(a) 文脈を精度に使う、は空席のままである。

**確定操作は必須ではない**（2026-09-22 に言い換え。旧稿は「確定操作は持たない」）。
FIFO は放っておいても回るので、**押さなくても書き進められる**。
編集可能な窓が後ろに滑っていくモデルは変わらない。
そのうえで Enter に**任意の早送り**を与える —— 明示的な確定を強制しないという思想は保たれる。

#### Enter は一段ずつ剥がす（2026-09-22 決定）

Enter が何をするかは、そのとき何を持っているかで決まる。**上から順に一段だけ**進める。

| そのときの状態 | Enter がすること |
|---|---|
| 変換済み未確定の文がある（1〜2 文） | **その文だけ**を、その時の状態のままホストへ確定して渡す。**打鍵中の文は何も変わらない** |
| 変換済み未確定の文が無く、打鍵中の文がある | **打鍵中のひらがなをそのまま**ホストへ渡す |
| どちらも無い | **改行**をホストへ渡す |

**これは標準 IME の Enter と同じ形である。** IME も「合成中なら確定、そうでなければ改行」で、
段が一つ増えただけになる。しかも二段目（ひらがなをそのまま渡す）は特別扱いではなく、
**IME で Space を押さずに Enter を押したときの挙動そのもの**である。
この設計では Space が変換しないので（§2.6）、打鍵中の文は常にその状態にいる。

二段目の意味づけはユーザー側にある。**「ここで Enter を押した」ということは、
本人の中では既に確定していた** —— つまり**ひらがなで書きたかった**、と読む。
通常の IME で無変換キーや F6 に割り当てられている操作が、ここでは自然に落ちてくる。

打鍵中の文を変えないのは、**その文がまだ句点に達していない**からである。
句点はユーザーが一区切りを付けた合図で（§2.3 冒頭）、Enter はその合図の代わりにならない。
Enter が確定できるのは「既にユーザーが区切りを付けたもの」だけ、という線で揃っている。

#### 「ひらがなを打ちたかった」が当たらない場合

二段目の読み替えは、**句点を打つつもりだった人には当たらない。**
そのための逃げ道が「文を区切る」役（上）である —— 変換キーを押してから Enter を押せば、
ひらがなではなく変換済みの文が渡る。Enter の三段は変えない。

### 2.4 マーク

マークは二系統ある。混ぜない。

#### (a) 誤打マーク — 打鍵中の文のみ・句点で判定する（2026-09-23 に改訂）

ローマ字入力は 1 モーラに複数打鍵を要するため、かな入力より誤打の機会が多い。
**「文がおかしいから直す」から「機械的にマークされた箇所を見る」への転換**は、
高速入力時の認知負荷を大きく下げる。変換前に検出できることに質的な意味がある。

**出自を書いておく。** これは §1 の「プロトコルの制約」から出た機能ではない。
既存の IME も未確定文字列を自分で持っているので、誤打を示すことはプロトコル上できる。
発想は「**誤打があったら簡単に戻って簡単に直したい。Mozc の UI 層にもあったらいい**」で、
この設計で必要度が上がったのは、**文をまるごとひらがなで持つ**（§2.2）ために
変な変換として誤打が表に出る機会が句点まで来ないからである。

**検出は強いマークだけにする**（2026-09-23 決定。§4.7 で測定）。

- **かなにならずに残った打鍵** —— `ka` → `ks` のように、ローマ字表のどこにも当たらず
  英字のまま出た打鍵。**誤打の 52% を拾い、誤打のない文を一度も止めない**（位置も全件合う）
- ~~異常に細かい文節分割（弱いマーク）~~ **退けた。** 誤打のない文を 9〜29% 止める。
  §8.8 の「書き手を止めない」と正面から衝突する
- 残りの 45% は、誤打が**別の正しいかな**になったもの（`えいがみに → えいがにに`）。
  Mozc の経路コストでの識別力は AUC 0.667 で、止める根拠にならない。
  「語として自然か」の判断なので、拾うなら §5 の空席の仕事になる。**いまは諦める**

**判定はエンジンの側で取る。読みの英字では見ない。** Shift で打った英字（`IME` / `note`）は
本文に普通にあるので、読みに英字があるかで見ると誤検出になる。配列エンジンの
`resolve`（`sequential-buffer.ts`）には、どの表にも当たらない先頭の 1 文字を
**そのまま出す**経路が既にあり、そこで印を付ければ正確に取れる。
**変換を要さない**ので、旧稿の「打鍵ごとに `convert` を呼ぶ」「末尾の文節は判定しない」は
どちらも要らなくなった（どちらも弱いマークのための規則だった）。

#### 句点で踏みとどまる（2026-09-23 決定）

**判定するのは句点（または「文を区切る」役）の瞬間だけ**である。打鍵中はマークを出さない ——
英字は打鍵中の表示にそのまま見えているので、重ねて示す必要が無い。

句点の時点で強いマークがあれば、**その文を変換せずに止める。**
句点は画面に残り、誤打の区間にマークが付く。**キャレットは動かさない**（末尾のまま）。

**句点を選んだ理由**は §2.3 と同じで、句点は書き手の中で一区切りが付き、**もともと手が止まっている
場所**だからである。新しい停止を作らずに、既にある停止を使う。

止めた後の**次の打鍵**で扱いを分ける。タイマーは使わず、**順序と位置で見る**（§2.6）。

| 次の打鍵 | 扱い |
|---|---|
| **←** | 誤打の区間の**右端**へ吸い付く（直しに入る）。区間が複数なら近い順（§2.4 の走査と同じ）。**末尾の句点を消す**（2026-09-24。下） |
| **句点をもう一度** | 止めた時と読みが**同じなら変換する**（誤打ではなかった・直さないの意思）。**変わっていれば判定し直す**。句点は 1 つしか入らない |
| **文字キー** | 先へ打ち進めたと見る。**止めた文を誤打ごと変換し**、打鍵は新しい文として受ける |
| **BS** | 句点を消して、打鍵中の状態へ戻る |

- **キャレットを飛ばさない理由**: 速い書き手は句点の直後に画面を見ずに次の文を打つ。
  キャレットが誤打の位置にあると、その打鍵が文の途中に刺さって文を壊す。
  止めはするが、**直しに入るかどうかは書き手が ← で決める**
- **右端に吸い付く理由**: 直しは BS から始まる。実測では英字の右端から BS するだけで
  直るのが 64%、右にさらに 1〜2 かな壊れているのが 35%（`りゅうgふぁう`）。
  エンジンが知っているのは英字の位置だけなので、そこまでは特定しない。見れば分かる
- **文字キーで流す理由**: 打鍵中の文は常に 1 つ（§2.2）。止めた文を持ったまま次の文を
  打たせると三層が崩れる。流すのは「見ていなかった」書き手を止めないためで、
  誤打はそのまま変換される（その後に直す道は作らない）
- **句点 2 回で変換するのは Space 2 連打（§2.6）と同じ形**である。誤検出はほぼ無い（§4.7）が、
  書き手が英字を意図して打った場合の抜け道になる

#### 直しに入ったら句点を消す（2026-09-24。実地から）

最初の実装は、← で直しに入っても文末の句点を残し、「途中で句点を打つ」か「→ で文末へ戻る」を
直し終わりの合図にしていた。実地で**「直した後に何をしたらいいかわからなくなる」**と出た。
句点を打てばいい、は発見できない —— **文末に句点が残り続けているので、もう一度打つ理由が見えない**。

**直しに入った時点で句点を消す**（← / Home で文末を離れたとき。BS で句点を消すのと同じ状態になる）。
すると直し終わりは**消えた句点を打ち直すこと**になり、これは標準 IME で文を終えるのと同じ動作なので
教えなくても辿り着ける。「なぜ句点を打つのか」が画面から読める形になった。

- 途中で句点を打った場合も、句点は途中に入らず**文末に入って**判定される
- → / End で文末へ戻っただけでは判定しない（句点が無いので）。旧稿の「文末へ戻る = 合図」は廃止
- 誤打が句点の直前にあると、句点を消した時点でキャレットはもう文末 = 誤打の右端にいる。
  この状態でもマークは出し続ける（直しに入ってから次の判定までは「直している最中」として扱う）

#### 見せ方: 目立たせない（2026-09-23 決定・2026-09-24 に調整）

**スペルチェッカーの赤い波線は、人を止めるために作られた装置である。**
ここでそれを踏むと 4a'' で得た手触り（§8.8）を壊す。

- **色を付けない。** 当初は打鍵中の文の破線下線を、その区間だけ波線に変える程度にとどめた
- **ただし破線の中の細い波線は見分けられなかった**（実地・2026-09-24。「注意深く見ればわかる」）。
  止まっている間と直している間は**文の破線を薄くする**（消すと、止まっている文が確定した本文と
  見分けられなくなる。未確定であることは下線が示している）
- **波線もやめた**（2026-09-24）。誤打は 1〜2 字なので、その幅の波線は波に見えず
  「傾きの狂ったよく分からない線」になる。**薄い背景**（文字色を薄く混ぜた灰）で塗る
- **マークの仕事は「見つけられること」であって「気づかせること」ではない。**
  本体は走査であり、マーク自体は走査の目印である
- 止まっていること自体は見える必要がある（句点が残ったまま変換されない、で分かる）

#### (b) 変換の不確実性マーク — 未確定の文のみ

**打鍵中の文には出さない。** まだ入力が完了しておらず、不確実なのは当然だからである。
インライン模型では打鍵中の文が変換されていないので、**そもそもマークの対象が存在しない**
（§2.2。旧案では方針としてこう決めていた）。
既存のライブ変換が与える「過剰にがちゃがちゃ動いて目障り」という印象は、
未完了の状態を逐一表示に反映してしまうことが要因の一部であり、そこを踏まない。

対象は三つ。**いずれも「正解が一意に決まる」ものに限る。**

- **区切りの揺れ** — N-best 経路が区切りで食い違っている
- **同音異義語** — 「解説する / 開設する」のように意味が違うもの
- **文書内の表記の揺れ** — 同じ語を、この文書の中で既に違う表記で書いている（§8.1）

**「どちらが正しいか」ではマークしない。** 「見る / 観る / 視る」「とき / 時」は意味がほぼ同じで、
正解が一意に定まらない（Mozc の `oss.tsv` が部分制約でしか書けていないのと同じ理由）。
このツールは表記の選択そのものを**許容する**立場を取る。思考の速度で書き出すことが目的であり、
表記の精密さは後工程（エディタ側の校正）に委ねる。

**しかし「文書の中で揺れている」なら、正解はこの文書が既に決めている。**
基準を「正しさ」から**「一貫性」**に読み替えると、正解が一意に定まる領域になる。
校正ツールの表記ゆれチェックが昔からやっているのもこれである。判定はモデルを要さない表引きで、
実装と限界は §8.1 にある。

**書き換えには使わない。マークだけに使う。** 台帳で候補を並べ替えると
「現在の文」で静かに効いてしまい、意図的な使い分け（「映画を観る」と「書類を見る」）を
黙って壊す。マークに限れば、揺れを指摘するだけなので使い分けは壊れない。

ユーザーが表記を決め打ちしたい場合は、確率ではなく**方針**の問題としてユーザー設定で指定する
（「『とき』はひらがな」等）。エンジンに聞くものではない。

#### マークへの到達

文字単位でキャレットを戻すとマークを探す作業自体が負荷になるため、
**次のマークへ / 前のマークへ**という線形走査を用意する。
マークがゼロになったら走査が終わる、という状態が分かりやすい。

打鍵中の文のマークと未確定の文のマークは意味が違う（前者は打鍵の異常、後者は変換の不確実性）ので、
見た目も分ける。

**到達はカーソルキー左右に割り当てる**（2026-09-22。ただし**役として持ち、配列ごとに
割り当て直せる** —— 60% キーボードでは矢印が Fn レイヤーにある。§2.6）。
矢印そのものを 1 文字ずつ動かすのではなく、**マークからマークへ吸い付く**。「文字単位で戻すのは負荷」という上の判断と矛盾しない ——
操作は矢印、意味は走査である。未確定スパンの端まで来たら、そこから先は通常のキャレット移動に戻る。

到達したマークの上で **Space** を押すと候補が出る（§2.5）。打鍵中の文では Space は空白を入れる
だけなので、**Space の意味が変わる境目は「マークの上かどうか」**になる（§2.6）。
境目はキャレットが吸い付いて止まる場所なので、見て分かる。
**誤打マークの上の Space は空白のまま**である（誤打マークは提示物を持たない。§2.5）。

**マークが一つも無いときの矢印は、この走査の対象ではない。** 打鍵中の文の中は普通に動き、
未確定スパンには止まる先が無いので入らない。マークが出て初めて走査が生まれる、という順序になる。

#### 到達しても直す手段が無い —— かなカーソルを入れる（2026-09-23 決定）

**打鍵中のかなは、末尾にしか足し引きできない。** 配列エンジン（`keymap-engine` の
`InputEngine`）が持っているのは `appendDirectKana`（末尾に足す）、`handleDeleteBack`
（`chars.pop()` = 末尾を削る）、`replaceDirectKana`（末尾から N 削って足す）だけである。

**つまり走査でジャンプしても、そこで直せない。** 誤打マークは提示物を持たない（§2.5）ので
「到達して打ち直す」が操作の全体なのに、その打ち直しができない。

三案を比べた。

| | やり方 | 評価 |
|---|---|---|
| A 巻き戻す | マーク位置から後ろを捨てて打ち直す | 実装は最軽量。**文頭の誤打で 20 字以上打ち直す**ことになり、§8.8 の「止めない」と最も遠い |
| B 尻尾を預かる | ジャンプ時にマークより後ろをホストが一時的に預かり、エンジンのかなを「マークまで」にする | エンジン無改造だが、**編集中だけ真実が二重化する** |
| **C かなカーソルを持つ**（採用） | かなバッファに本物のカーソルを入れる | 層をまたぐが、模型としては唯一素直 |

**B を退けた理由を残す。** 一見エンジン無改造で済むが、
`pump()` が拠って立つ前提（**エンジンの `composingKana` が打鍵中の文そのもの**）が
編集中だけ崩れる。句点・Enter・区切る・FIFO がその最中に来たときの規則を全部足すことになり、
§2.2 で「routing のためにかなはエンジンが持つ」と決めた**単一の真実が二重化する**。

**C の代償は層をまたぐこと。** 正典は labo の `web/src/engine/input-engine.ts` で、
hechima/site は **keymap-engine v2.5.0 を pin して vendoring** している。
`VENDOR.md` の原則「**1 レイヤだけ上げ下げしない**」に触れる。

そして本体は**インデックスの追加ではなく、ローマ字リゾルバとの相互作用の定義**である。
象徴的なのが `repend()` —— かな削除後に**末尾の英字列**を見て未確定バッファへ戻している。
カーソルがあれば「カーソルの手前」を見ることになる。同種の末尾前提が
追記 6 箇所・末尾削除 2 箇所・`applyPostModify`（濁点トグル / 小書き、末尾 1 文字）にある。
フリックとゲームパッドが `replaceDirectKana` / `applyPostModify` を実際に使っている
（Obsidian プラグインで稼働中）ので、壊すと実害が出る。

**二段に割る。デメリットは全部 2 段目に集まる。**

1. **カーソルを持つだけ**（既定 = 末尾、移動 API 無し）。**既存挙動は完全に不変**なので、
   labo の `golden.test.ts` と配列別テスト（NICOLA / 親指ぴゅん / sequential-buffer /
   phase / gamepad）を緑のまま入れられる
2. **移動と途中挿入**。ここで `repend` / `applyPostModify` / chord バッファの規則を決める
   （同時打鍵の窓が開いている最中の移動は未定義。おそらく「移動で chord を流す」）

**実装した移動の規則（2026-09-23・2 段目）**:

- **動かす前に進行中の入力をいまの位置で閉じる。** ローマ字の途中は出し切り（かなにならなければ
  英字のまま残り、誤打マークに載る）、同時打鍵の窓は閉じる。先出しした文字の差し替えは
  「カーソルの手前を N 字消して挿す」なので、動いた後に来ると別の文字を消す
- **← / → はマークの右端へ吸い付き、行き先のマークが無ければ 1 文字ずつ動く。** Home / End は文の端へ。
  配列が出す ← / →（薙刀式の T / Y）も同じ扱い。打鍵中の文が空ならホストのキャレット移動に戻る
- **直している最中（カーソルが文末に無い間）は文を切り出さない。** 句点が末尾にあっても変換しない
- **直しに入ると句点が消え、直し終わりの合図は句点を打ち直すこと**（2026-09-24 に改訂。§2.4(a)
  「直しに入ったら句点を消す」）。途中で打った句点は文末に入る。→ / End で文末へ戻っただけでは判定しない。
  判定で誤打が残っていればまた止まる
- 直している最中の Enter はひらがなのまま渡す（§2.3 の二段目。流れたに数える）
- Delete は飲む（カーソルの後ろを消す口がエンジンに無い）

手順は四手になる: labo でカーソルを入れる → 版を上げる → hechima へ再 vendoring
（`VENDOR.md` / `EMBEDDING.md` の版の組み合わせも更新。版はビルド時に
`check-versions.mjs` が機械照合する）→ 走査の器とマークを載せる。

**（2026-09-21・実地）この走査は任意要素ではない。** 器だけを打ってもらった時点で
「**誤打マークがとても早く出る、あるいはカーソルキー左等で任意の場所の誤打のみ補正できないと辛い**」
という報告が出た。走査が無いと、誤りに気づいても直せないまま流れていく。

報告の「任意の場所の**誤打のみ**」は、この節の「文字単位で戻すのは負荷なので線形走査にする」と
同じ結論に独立に到達している。設計の方向は合っていて、**欠けているのは実装だけ**である。

実装順としても、マークの中身（何を検出するか）より**走査の器のほうが先**でよい。
器があればマークは差し込める。逆は成り立たない。

### 2.5 候補の提示

**見た目は標準 IME の候補ポップアップ、中身は経路の並列。**
マークの上で Space を押すと、キャレットの下に候補が出る —— 形は誰もが知っているものにする。

§1 と矛盾しない。§1 の制約は「**プロトコルが**区切りの違う候補を運べない」ことであって、
ポップアップという形が悪いのではない。hechima は自前で描くので運べる（§1「プロトコルの外にいる」）。
つまり**馴染みの枠に新しい中身**を載せる形になる —— これが §8.7 の「寄せ先」の答えでもある。

マーク種別ごとに提示物が異なる。

**区切りの揺れ** — N-best 経路を**区切りでグループ化**し、各グループの最良経路を代表として提示する。
区切りを抽象的に見せてもユーザーは選べないので、実際の文を読ませる。

```
① ここで|履物|を|脱ぐ
② ここでは|着物|を|脱ぐ
```

**実装（2026-09-25）**: 印の区間の中だけを `ここで|履物を` のように区切りを見せて並べる。先頭はいまの区切り
（選ぶと「確かめた」として印が消える）。Space / ↓ で次、↑ で前、Enter か数字で決定、Esc で閉じる。
選ぶと**その区間だけ**が差し替わる（区間の外は変換のまま）。書き換えはユーザーが選んだときだけなので、
§2.2 の「自動修正はしない」は保たれる。

**候補はコストの崖で切る。** 経路のコストには崖があり、「ここではきものをぬぐ」では 2 位の差が 721、
3 位以降は 2405〜6823 だった。崖の向こうは `ここで|破棄|者を` `個々|デ|履物を` のような読めない候補になる。
**印のゲートと同じ重み（λ=500 のソフトマックス）で最良の 2% 未満を出さない**（いまの区切りは常に残す）。
候補の二層化（labo `docs/hechima-candidate-fold-design.md`）が「1 位からのコスト差で切る」を採ったのと同じ判断である。

**走査**: 打鍵中の文の先頭（空なら最初）で ← を押すと、いちばん新しい印へ吸い付く。← / → で印から印へ、
いちばん右の印から → で打鍵中の文へ戻る。文字を打てばそのまま打鍵中へ戻って打てる。

区切りの異なる経路どうしは見た目がはっきり違うため、選択肢としての重なりが小さい。
これは細部だけが違う経路を並べる場合と対照的で、この UI が区切りを標的にする理由の一つでもある。

**誤打マーク** — **候補は出せない**（2026-09-23 に明記）。
機械は「打ち間違えた」ことは分かっても**何を打ちたかったかを知らない**ので、
「もしかして」を出す材料が無い。したがって誤打マークだけは提示物を持たず、
**到達して打ち直す**のが操作の全体になる。§2.5 が (b) の三種しか書いていなかったのは
書き落としではなく、**そもそも出すものが無い**ためだった。

だから誤打マークでは**直す手段のほうが本体**になる（§2.4「マークへの到達」）。

**同音異義語** — 該当文節の候補リスト。

**文書内の表記の揺れ** — 該当文節の候補リストに加えて、**この文書で先に使った表記**を示す。
「どちらが正しいか」ではなく「この文書では既にこう書いた」という提示なので、
先例そのものを見せないと判断材料にならない。

```
濫用        ← いま
  この文書では「乱用」（3 文前）
```

選ばなければ揺れたままになる。それでよい —— §2.4 のとおり書き換えはしない。

**漢直・新配列との統合（任意）** — マーク箇所に対して候補リストだけでなく
「その字の打ち方」をガイドに出せば、選択ではなく直接入力で直せる。
漢直使用者には候補を探すより速い場面がある。`replay-engine` のキーボード図 SVG
ビジュアライザを流用できる。

### 2.6 表示制御とキーの割り当て

**配置の問題は消えた。** 本文を覆うものが無いので、どこに置くか（旧案の案 A / 案 B）も、
どう隠すか（ホバーで半透明）も要らない。残った論点は**キーの割り当て**で、
2026-09-22 に決めた（Enter は §2.3、Space はここ）。

#### Space は空白を入れる。変換はしない（2026-09-22 決定）

**打鍵中の文で Space を押したら、空白が入る。** 変換は走らない —— 変換は句点が担う（§2.3）。

**これは Space キー本来の意味である。** 日本語入力では数十年にわたって
「入力中に Space を押したら変換が走る」が当たり前だったので**新しく見えるが、
実際には元に戻っただけ**である。覚えることが増えるのではなく、例外が一つ減る。

**マークの上では「候補を出す」。** カーソルキーでマークへ移動した状態（§2.4）で押すと、
候補ポップアップが出る（§2.5）。ここだけは IME に似る。
Space の意味が場所で変わることになるが、**変わり目はマークの上かどうか**で、
そこはキャレットが吸い付いて止まる場所なので、見て分かる。

| どこで押したか | Space |
|---|---|
| 打鍵中の文 | **空白を入れる** |
| マークの上 | **候補を出す**（§2.5） |

**変換は変換キーがやる。** 句点を打たない入力のために「文を区切る」役を別に持たせてある
（§2.3。既定は JIS の変換キー / US は修飾キー単押し）。
Space から取り上げた仕事が、名前のとおりのキーへ戻った形になる。

#### Space 2 連打も区切る —— 壊した反射の受け皿（2026-09-22 決定）

**空白が二つ並んだら、1 つ目を消して「文を区切る」を送る。**
変換キーの別名ではなく、**Space = 変換 の反射を受け止めるための道**である。

反射で押した人がたどる道はこうなる。

```
けんさくご  →[Space]→ けんさくご␣   変換されない・空白が入る（ここで学ぶ）
            →[Space]→ 検索語        区切られる・1 打目の空白も消える（ここで救われる）
```

**間違った操作を繰り返すと正しい操作になる。** 学習信号（空白が入る＝変換ではない）と
救済（区切られる）が同じキーに乗っていて、順に出てくる。
しかも **Space = 空白 を身につけた人にはこの例外が一生見えない** ——
日本語の散文で空白を二つ続けて打つことはまず無いからである。
§2.6 冒頭の「例外が一つ減る」は、**その例外を必要とする人にだけ戻ってくる**形になる。

**判定は時間ではなく位置で行う。**「一定時間内に 2 回」ではなく
「**読みの末尾が空白で、そこにもう一つ空白が来た**」。
§2.6 は長押しを退け、§2.3 はタイマーによる状態変化を退けているので、ここで閾値を持ち込むと
方針が崩れる。位置判定なら「空白が二つ並んだら区切る」とそのまま説明できる。

**空白しか無いときは発火しない。** これが無いと Markdown のハード改行（行末の空白 2 つ）を壊す。
句点の直後は打鍵中の文が空なので、そこで空白を二つ打っても区切る対象が無く、
**空白がそのまま残る**。用途が衝突しないのはこの条件のおかげである。

**代償: 日本語の文中で空白を二つ続けて打てない。**
意図的な 1 つの空白は残る（消えるのは直前の 1 つだけなので「けんさく␣ご」は壊れない）が、
二つ並べる書き方はできなくなる。日本語の散文を対象にしているので割に合うと判断した。

この設計でコンポーザが持つ役は、結局この四つだけである。

| 役 | 既定 | すること |
|---|---|---|
| 空白 | Space | 空白を入れる（マークの上でだけ候補を出す） |
| 文を区切る | 変換キー（JIS）／ **Space 2 連打** | 句点と同じ合図を、文字を伴わずに送る |
| 確定 | Enter | 一段ずつ剥がす（§2.3 の表） |
| マーク走査 | カーソルキー左右 | マークからマークへ吸い付く（§2.4） |

「文を区切る」に入口が二つあるのは冗長ではない。**変換キーは覚えた人の道、
Space 2 連打は覚えていない人の道**で、後者は前者へ渡すための踏み台である。

#### 書くだけなら専用キーが要らない（60% キーボードでも成立する）

この四つのうち**書くために要るのは上の三つだけ**で、しかも既定は
**Space と Enter と英数字**で閉じている。専用キー（変換 / 無変換 / かな）は**無くてよい**。

意図した設計ではなく、**Space の役割を本来のものへ戻したことの帰結**である。
変換を Space から外した結果、変換キーが「あれば便利」の位置に落ち、
Space 2 連打が既定の入口として残った。

ただし**四つ目（マーク走査）だけは矢印が要る。** 60% キーボードでは矢印が Fn レイヤーに
あるので、ここだけ操作コストが上がる。つまり:

| | 60% キーボードで |
|---|---|
| **書く** | 完全に成立する。Space / Enter / 英数字だけで閉じる |
| **直す** | 矢印が要るので Fn レイヤー越しになる |

**直せないと「使えない」が他の評価を覆う**（§4.4b の成立条件）ので、これは軽い話ではない。
マーク走査も**役として持ち、配列ごとに割り当て直せる**ようにする ——
他の三つと同じ扱いであり、左右矢印はあくまで既定である。

**Vim 風の割り当て（`h` / `l` 等）はあり得るが、現時点では対象外**（2026-09-22）。
60% キーボードを使う層とは相性がよさそうだが、モードを持ち込む話になるので今は踏み込まない。
**役として持ってさえいれば後から足せる**ので、いま決める必要が無い ——
これがキーを役で持つことの実利である。

#### この決定は IME の反射を一つだけ裏切る

寄せ先を IME に決めた（§8.7）のに、**いちばん訓練された反射（Space = 変換）を破る**。
ここは正直に認める。

緩和になっているのは、**空振りしないこと**である。押すと空白が入るので、
「変換されないんだ」が一度で分かる。**何も起きない**のがいちばん悪く、それは避けられている。

**実地の手応え（2026-09-22）: 「ちょっと不思議」で収まった。**
「変換のつもりでスペースキーを押すと空白が入るってのがちょっと不思議」という report で、
**破綻ではなく違和感の水準**に落ちている。緩和は効いていると見てよい。
ただし違和感そのものは残っているので、ここは解消済みにしない。

#### 割り当ては固定にできない（新配列）

新配列使用者はほぼ全てのキーに意味を割り当てており、**Space は最も衝突する側のキーである**
（薙刀式のように Space を同時打鍵のシフトに使う配列が多い）。その場合 Space は配列エンジンに
食われてコンポーザまで届かない。

したがって上の表は**逐次配列での既定**であって、固定ではない。
「候補を出す」は**役**として持ち、物理キーは配列ごとに割り当て直せるようにする。
`hechima-keymap` の `analyzeKeymap()` が配列 JSON から特徴を読み出せるので、
**読み込んだ配列定義から空きキーを提案する**ことができる。

長押しを使わないのも同じ理由である。Space は文字を産むキーなので、
長押しはキーリピートで空白が並ぶ。

#### タイマーによる自動変化は採用しない

「思考のために止まった」と「書き終わった」を区別できず、日本語を書いていれば数秒の停止は頻繁に起きる。
そのたびに UI が変化すると、常時表示より不快な視覚ノイズになる。
状態変化はユーザーが原因を説明できるものだけにする。

インライン模型で状態が変わるのは**句点を打ったとき**（変換）と**4 文目に入ったとき**（確定）だけで、
どちらもユーザーの打鍵が原因である。この条件はこの模型では素直に満たされる。

#### ホストアプリの本文は読み取らない

自分が打った未確定分の外へは手を出さない。見たいものには他者の書いたもの
（SNS の相手の発言など）が含まれ、それは自分の持ち物ではない。技術的可否以前の線として引く。

### 2.7 任意要素: キー入力ガイド

論理配列（新配列）・漢直・`gamepad-engine` のビジュアライザを置ける。
`replay-engine` 同梱のキーボード図 SVG ビジュアライザ（物理配置プロファイル＋押下ハイライト＋
手指オーバーレイ）を流用する。新配列の習得期には実質的な価値がある。
画面占有が増えるため既定はオフ。

**置き場が変わった。** 旧案では 1行欄の下に添えていたが、その1行欄が無い。
ビジュアライザは参照物なので**動いてはいけない** —— キャレットに追従させると
動く鍵盤図を目で追うことになる。テキストの流れの一部ではないので、
画面の固定位置（下端など）へ分離して置く。旧案の案 B で同じ結論に達していたのと同じ理由である。

### 2.8 旧案（矩形オーバーレイ）を捨てた記録

2026-09-21 までの §2 は、**ホットキーで出る固定サイズの矩形オーバーレイ**だった。
1行欄（ひらがな・右端キャレット固定）と 6 行の矩形（変換済み）を縦に積み、
画面中央固定（案 A）かキャレット追従（案 B）で配置する、という形である。

捨てた理由は実地で出た**概念の学習コスト**（§8.7）で、いちばん強く出たのは
「バッファを溢れた文が本体に流れているかどうかすら、慣れるまではまったく分からない」だった。
インライン模型ではテキストが動かず、確定は下線が消えるだけなので、この穴は塞がる
（ただし実地では未確認）。

**一緒に落ちたもの**: 矩形の寸法（幅 40 字 × 6 行）とその固定高の決定、
バッファと窓を分ける議論、1行欄と矩形の切れ目を文節境界に取る規則、
配置の案 A / 案 B とその比較（§4.4）、ホバーで半透明にする隠す操作。

**測ったものは無駄になっていない。** §4.6 の文長分布は問いが変わって生き残る。

| 旧案での問い | インライン模型での問い |
|---|---|
| 矩形は何行あれば 3 文が見えるか（→ 6 行） | 未確定スパンは常時どれくらいの長さか（中央値 23〜31 字 × 3 文 ≒ 70〜90 字） |
| 1行欄に 1 文まるごと残るか（→ 72.2%） | 生ひらがなのまま打ち切る文はどれくらいか（同じ数字が使える） |

実装（`site/src/composer/`）も半分は生きる。`flow.ts` の句点切り出し・3 文バッファ・FIFO は
そのまま使え、`block.ts`（矩形）と `placement.ts`（配置）、および `flow.ts` の窓の分割が落ちる。

## 3. エンジン側の要件

### `hechima-wasm` に N-best 経路 API を追加する

現状の「かな → 文節/候補 JSON」では、**区切り違いを含む経路単位の候補**が表現できない。
この UI の中核が成立しないため、ここが唯一の下層改修となる。

必要な出力（経路ごと）:

- 区切り位置の列
- 各文節の表記（および読み）
- **経路コスト**（1位との差＝マージンが取れること）

Mozc 側には既に `converter/immutable_converter_main.cc` がラティスをダンプする実装がある。
出力ヘッダは以下で、ノードごとに `wcost` / `cost` とリンク構造を持つ。

```
id  key  value  begin_pos  end_pos  lid  rid  wcost  cost  bnext  enext  prev  next
```

**ImmutableConverter は rewriter を通っていない**ことが重要である（rewriter は上位の Converter が
後から被せる層）。後述のとおり `cost` の意味が均質になるため、マージンを扱うならこの層が望ましい。

グループ化（区切りでまとめて代表経路を選ぶ）は JS 側で行う。WASM 側は経路をそのまま返す。

### 実装状況（2026-09-20）

`logical-layout-labo/hechima-wasm/hechima_wasm.cc` に `hechima_paths` を実装済み。
ネイティブ（aarch64 Linux）でビルドと自己テストまで通っている。wasm 版は CI での焼き直しが要る。

```
hechima_paths(kana, max_paths, expand)
→ {"paths":[{"base":true,"cost":17573,"sizes":[4,3,2],
             "segments":[{"key":"ここでは","value":"ここでは"},...]}, ...]}
```

**分節を揺らさない。** ラティスは 1 回組めば全ての区切りを含んでいるので、
揺らして変換し直すのは無駄な労力になる（そこまでの段階で既に分節が決まってしまっている）。

1. `ImmutableConverter::Convert(options, &segments, &lattice)` —— ラティスを受け取れる
   公開オーバーロードでラティスごと取る
2. Mozc 自身の `NBestGenerator` を **[BOS, EOS] の全域**に当てる
   （`ONLY_EDGE` + `FILL_INNER_SEGMENT_INFO` = リアルタイム変換と同じ設定）。
   1 候補 = 全文 1 経路で、内部の文節境界が載る
3. 同じ区切りの経路は初出（= その区切りの最良）だけ残して畳む

`cost` は A\* が出す**本物の経路コスト**なので、区切りの異なる経路どうしを直接比較できる。

`engine::Modules` は `Engine::GetModulesForTesting()` から借りている。
名前のとおりテスト用の口なので、上流の変更で消える可能性がある（要注視）。

**候補の一覧は返さない。** 区切りを選んだ後の候補は既存の
`hechima_convert2(kana, sizes_csv, max_cands)` で取る（`sizes` をそのまま渡せる）。
役割を分けてあり、`hechima_paths` は「どの区切りか」だけを速く決める。

#### 実測（2026-09-20 / 10 入力）

| 項目 | 結果 |
|---|---|
| base が cost 1 位 | **10 / 10** |
| 2 位とのマージン | min 103 / 中央値 880 / max 4632 |
| レイテンシ | **1〜5ms**（10〜16 文字） |

```
base  cost=17573  ここでは | 着物を | 脱ぐ
      cost=18294  ここで   | 履物を | 脱ぐ      （+721）
base  cost=23308  庭には | 庭   | 鶏が | いる
      cost=23976  庭に   | 埴輪 | 鶏が | いる    （+668）
```

マージンは素直に散っている。「すもももももももものうち」が +103（本当に曖昧）、
「かれがくるまでまつ」が +4632（自信あり）。§4 の観測量として機能しそうに見える。

> **失敗した最初の実装（記録）**
>
> 当初は公開 API だけで済ませようとして、`StartConversion` + `ResizeSegments` で分節を
> 揺らし（境界をずらす・結合・分割のビーム探索）、`Candidate::cost` の総和を経路コストの
> 代用にした。**これは使えない。** `Candidate::cost` は「その文節の部分ラティスの中での」
> コストなので、足しても経路コストにならない。実測（同じ 10 入力・各 40〜60 経路）:
>
> - 総和が最小になる経路は 10/10 で base より文節数が少ない（文節が 1 つ増えるごとに中央値 +5640）
> - base は総和の順位で 4〜31 位 / 40〜60 本。**同じ文節数に限っても** base が 1 位は 2/10
>
> レイテンシも 97ms かかっていた（ラティス版は 1ms）。
> 教訓として、**per-segment のコストを足して経路コストを名乗らせない**こと。

### 注意: Mozc の `cost` は較正された確率ではない

コストは原理的には -log 確率（単語生起コスト＋連接コストの和を Viterbi で最小化）であり、
差は対数尤度比に対応する。順位付けのためだけの順序数ではない。
しかし最終的な `cost` フィールドに入る値は、以下の理由で確率的解釈が崩れている。

- **定数のベタ書き** — 例: `rewriter/single_kanji_rewriter.cc` で単漢字候補に `cost = 5000`。
  rewriter 群には cost を直接操作する箇所が 30 以上ある
- **変換後の上書き** — `converter/candidate.h` に `cost_before_rescoring` があり、
  `engine/supplemental_model_interface.h` の `RescoreResults()` で再スコアリングされうる
- **ユーザー学習** — 履歴による順位調整も同じフィールドに乗る
- **正規化されていない** — パスコストは候補全体で正規化されていないため、
  差から比は出せても「正解である確率」は出ない
- **モデル誤設定** — n-gram が捉えられない依存については、コスト差は「自信」ではなく
  **モデルの盲点**を反映する。マージンが大きくても間違えるのはこのため

結果として、一つの整数フィールドに確率由来の値とヒューリスティック由来の値が同居している。
Mozc は**論拠（確率）と方針（これは出したい）を同じ `cost` に畳み込んでいる**ため、後から分離できない。

実務上の帰結:

- **マージンを閾値に使うなら ImmutableConverter 層で取る**（rewriter 混入がゼロ）
- 上位層のコストを使う場合は、日付・記号・単漢字・絵文字・計算結果を対象から除外する
- 閾値は理論的に決まらない。**実データで切る**（§4）

## 4. 実験計画

UI を作る前に、Mozc だけで取れる数字を先に取る。
これを飛ばすと、個別の失敗を個別の補正で潰していく作業になり、
効いているかどうかを判定する指標が永久に手に入らない。

### 4.1 評価データ

`fcitx5-mozc` に同梱のものをそのまま使える。

| ファイル | 件数 | 内容 |
|---|---|---|
| `data/dictionary_oss/evaluation.tsv` | 602 | **全文の変換結果**つき。`status / input / output / command / argument / version`。**採点には落とし穴がある（下記）** |
| `data/test/quality_regression_test/oss.tsv` | 501 | 部分制約（`Conversion Match` / `Not Match`）。既知の誤変換パターンの列挙 |
| `data/test/quality_regression_test/regression.tsv` | 102 | 同上 |
| `data/test/quality_regression_test/myoji.tsv` | 50,614 | 名字専用。今回は対象外 |

`evaluation.tsv` は当時の出力スナップショットにバージョン番号が付いているため、
**現行ビルドとの差分を取るだけで回帰の有無が分かる**。最も扱いやすい。

なお Mozc の品質回帰テストは全文の正解を書かず、部分制約（含むべき／含むべきでない）で
書かれている。正解が一意に定まらない領域があるためだが、副作用として
**個別の補正がテストによって固定化され、外せなくなる**構造を生んでいる。
この評価セットを使う際は「既知の失敗の禁止リスト」であって「正解の定義」ではないことに注意する。

**採点の落とし穴 —— `argument` は「1 位に来るべき値」ではない。**
`command` 列 `Conversion Expected N` の **N は「`argument` が上位 N 位までに出れば合格」**を意味する
（`converter/quality_regression_util.cc` の `GetRank` / `expected_rank`）。
`Conversion Expected*` の 509 件のうち **217 件（42.6%）は N>0** で、1 位を要求していない。

```
しょうてん → 商店 が正しい。argument「笑点」は上位 9 位までに出ればよい
```

完全一致で採点すると、この 217 件は仕様どおりの挙動でも誤りに数えられる。
**内訳を取るときは N==0 の 292 件に絞る**（§4.2b）。

### 4.2 先に取る数字

**(1) 区切りの取り分（旧「経路マージン」「区切りの事後確率」）**

当初は「1 位経路と 2 位経路のコスト差」を観測量にする予定だったが、**差だけでは足りない**。

まず前提として、**コストは対数領域の量なので、比ではなく差を見るのが正しい**。
差がそのまま対数尤度比になる。絶対コストで割ってはいけない —— 絶対コストは
文長にほぼ比例するだけの量で（10 入力で字数との相関 0.635、1 字あたり約 1700）、
割ると長い文のマージンが不当に小さく見える。

問題は別のところにある。**対抗馬は 1 本とは限らない。**

| 読み | Δ2位 | 区切り数 | baseShare λ=500 |
|---|---|---|---|
| ここではきものをぬぐ | 721 | 9 | 0.803 |
| にわにはにわにわとりがいる | 668 | 11 | 0.674 |
| あのひとはいしゃだ | 880 | 12 | 0.814 |
| くるまではこをはこぶ | 872 | 7 | 0.849 |

生の差はほぼ同じでも、対抗馬の本数で取り分は大きく変わる。
Δ で並べた順位と取り分で並べた順位は実際に入れ替わる。

なので観測量は**区切りの取り分**にする。

```
share(区切り_i) ∝ Σ_{その区切りを持つ経路 p} exp(-cost(p) / λ)
```

**`P(...)` とは書かない。** これは列挙した経路の重みの総和に対する取り分であって、
確率ではない（名前の決定は §9.2）。分布の集中度を見る形で、
これは Jev の Choice の confidence と同じ量である。

**Σ を取る（周辺化する）ことが要る。** ある区切りの尤もらしさは、その区切りを持つ経路
すべての重みの和であって、最良 1 本ではない。実測では最良 1 本だけを使う場合と比べて
`baseShare` が最大 ±0.14 動いた（「すもももももももものうち」+0.117 /「このみかんはおいしい」-0.138）。
`hechima_paths` は `npaths` と `costs`（その区切りを持つ経路のコスト列、最大 32 本）を
返すので、ホスト側で任意の λ で計算できる。

**λ はソフトマックスの温度**（コスト → 重みのスケール）。これがこの実験の唯一の自由パラメータになる。
λ は実質「対抗馬の本数をどれだけ重く見るか」のつまみで、λ→0 で「マージンだけ」、
λ→∞ で「区切りの本数だけ」に漸近する。**λ は実データでゲート性能に対して決める**
（「正解確率に対して較正する」とは呼べない。理由は §9.2）。

**(2) マージン別の正解率（信頼性図）**
マージンを分位で切り、各ビンでの正解率をプロットする。
**この図がこの実験の成否を決める。**

- **単調に上がる** → コスト差には情報がある。マージンをゲートとして使えるし、閾値を切る意味がある
- **寝ている** → 実質的に順位付けだけの量。マージンゲートという設計そのものが崩れる

→ **単調に上がった**（§4.2b の較正表）。ただし絶対値としてはずれている。

**(3) マージン小の部分集合における正解率**
上積みの余地を直接示す数字。

- **50% 近い** → コイン投げ状態。Mozc のコストがそこで情報を失っている。理想的な標的
- **80% ある** → マージンが小さくても Mozc は当てている。抜くのは難しい

**(4) 区切りで割れている頻度**
N-best 経路の上位が区切りで食い違うケースの割合。
これがこの UI の中核機能が働く頻度そのものになる。

**(5) 誤りの内訳**
1位経路と正解経路の差分を「区切りが違う / 単語が違う / 両方 / 未知語」で分類する。
文節ごとに正誤を数えるのは Mozc の構造（経路探索）に合っていない。

未知語は**候補に存在しない語**であり、この UI では原理的に救えない
（カバレッジのボトルネックは辞書側にある）。内訳から除外して考える。

→ 実測では**ほぼ存在しなかった**（C3 = 0.3%、§4.2b）。この層で解けない問題は想定より少ない。

**取り分で絞る必要がある。**

**マークのゲート性能（§4.2 (2)(3) / §4.5）**

`baseShare < しきい値` でマークしたときの性能（λ=500）:

| しきい値 | マーク率 | 救えるケースの捕捉率 | マークの適合率 |
|---|---|---|---|
| 0.7 | 9.6% | 70.6% | 82.1% |
| **0.9** | **17.8%** | **88.2%** | **63.5%** |
| 0.99 | 37.0% | 94.1% | 47.2% |
| （全件マーク） | 100% | 100% | 31.8% |

**`baseShare < 0.9` で、6 文に 1 文をマークして救えるケースの 9 割弱を捕捉できる。**
適合率 63.5% はベースの誤り率 31.8% のちょうど 2 倍。校正ツールのゲートとしては使える水準。

**`baseShare` が何を測っているか（重要）**

*較正*: 単調には上がる。絶対値としては合っていない。

| baseShare | 実際の正解率 | 件数 |
|---|---|---|
| 0.000–0.500 | 25.0% | 8 |
| 0.500–0.900 | 38.6% | 44 |
| 0.900–0.990 | 67.9% | 56 |
| 0.990–0.999 | 73.6% | 53 |
| 0.999–1.000 | **78.6%** | 131 |

§4.2 (2) の合格条件（単調に上がる）は満たしている。ただし `baseShare`≈1.0 でも実際の正解率は 78.6% で、
**確率としては読めない**。

*識別力（AUC, λ=500）*:

| 何を予測するか | AUC |
|---|---|
| base が正解か | **0.677** |
| 救えるケースか（base 誤り かつ 別経路に正解） | **0.889** |

**「正解が近くにあるか」（0.889）のほうが「base が正しいか」（0.677）よりはっきり効く。**
`baseShare` は「Mozc のモデルの下で、分節に配られた重みがどれだけ base に集中しているか」であって、
「モデルが正しいか」ではない。この 2 つがずれるのは**モデルが自信満々に間違えるとき**で、
n-gram が捉えられない依存についてはコスト差が自信ではなくモデルの盲点を反映する
（§3「`cost` は較正された確率ではない」と同じ話）。

一方、モデルが迷っているときは対抗馬の中に正解が混じっている確率が高い。だから
「正解が近くにあるか」には 0.889 で効く。**このゲートは「base は誤り」ではなく
「正解があるとすれば近くにある」と言っている。**

実務上の線引き:

- ○ 「下位 20% をマークする」（予算配分の判断）
- ○ 「`baseShare < 0.9` なら代替を出す」（代替を出す価値があるかの判断）
- ✗ 「`baseShare` = 0.99 だから安全、マークしない」（実際の正解率は 78.6%）
- ✗ Jev の分布と足すとき両方が較正済みと仮定する（§5。λ はスケール換算だけでなく
  **較正のずれも吸収する**必要がある = 理論的には決まらない）

**製品 Mozc との差（2026-09-21 に実測）**

**救える余地の比較（製品 Mozc に対する上積み・母数 292）**

| | 上積み |
|---|---|

どちらも**上限値**であることに注意する。提示されたものをユーザーが正しく選べるか、
提示そのものが邪魔にならないかは別の問題で、そこは §7 のとおり `replay-engine` の
`hlog-1` で修正操作の回数を取って測る。

### 4.2e この測定で分からないこと

`evaluation.tsv` は**単文**である。したがって §5 で空席にした「文をまたぐ文脈を使った判断」は
**このデータでは原理的に測れない**。ここで測れるのは「文内の判別器として Mozc の n-gram より
強いか」だけで、それは妥当そうだが未証明。

同じ理由で、**§8.1 の台帳の効き目も測れない**。台帳の価値は「表記ゆれの発生率 ×
文書内で同じ `content_key` が再出現する率」だが、後者は単文のデータには存在しない。
測れたのは前者（C1 の 19.7%）だけである。

外部モデルの固有の価値を測るにも、**曖昧さが文をまたぐ複数文のデータ**が要る。
既存の評価セットにそれは無いので、作るところからになる。

### 4.3 天井の事前計算

```
全体への寄与 = (マージン小の割合) × (その部分集合での誤り率) × (改善できる割合)
```

最初の二項は上記の測定だけで出る。天井が低ければ、UI を作る前に分かる。

→ 出た。**5.8 ポイント**（§4.2c）。低いが、§4.2b のとおり
**誤変換に遭遇したときの 18.3%** という読み方のほうが体感に近い。

### 4.4 ~~配置の比較~~ 消えた（2026-09-22。結論の記録）

旧案の案 A（画面中央固定）と案 B（キャレット追従）を実地で比べる計画だった。
**インライン模型に移ったので、比べる対象そのものが無くなった**（§2.8）。
節ごと削らずに残すのは、**この比較が何を教えたか**が後で効くからである。

**教わったことは二つ。**

**(1) 比較が成立する条件を書いていなかった。** 器を作れば比べられる、と思っていたが、
実地の報告は「A/B どちらがいいか、という判断は、現時点ではまったく判断できない。
アプリの概念が新しすぎて、慣れるまでが難しい」だった。**学習コストが交絡すると、
比較したい差はその下に埋もれる。** 以後の比較（§4.4b）には成立条件を先に書く。

**(2) 軸を取り違えていた。** 見ていたのは「どちらが快適か」（視線の固定・被覆面積・
隠す操作の量）だったが、先に来るのは**「どちらが説明不要か」**だった。
その軸では案 B（既存 IME のメンタルモデルに近い）が有利で、
**その判断を突き詰めた先がインライン模型そのものである** —— 案 B の極限は
「キャレットに追従する矩形」ではなく「キャレットの位置に直接書く」だった。

### 4.4b インライン模型で比べるもの（未実施）

比較の対象が「配置」から「**どこまでを未確定のままにするか**」へ移る。

| 比べるもの | 候補 |
|---|---|
| 未確定で保持する文の数 | 1 文 / 3 文（§5 の (b)(c) が根拠だが、実地では未検証） |
| 変換のトリガー | 句点（§2.3 の決定） / 句点の次の 1 文字（旧案の規則） |
| Space と Enter の割り当て | §2.6 の三案 |

**成立条件**（(1) の教訓）:

- 誤りを直せること（§2.4 のマークと走査）。直せないと「使えない」が他の評価を覆う
- ~~確定が起きたと分かること（§2.1）~~ **✅ 解消（2026-09-22・実機）。**
  「確定したことの明示も、下線の消失で十分機能している」。**穏やかすぎて気づかない**という
  懸念は外れた。旧模型の最大の穴（§2.8「バッファを溢れた文が本体に流れているかどうかすら
  分からない」）が、テキストを動かさない模型に移したことで実際に塞がっている

体感の評価は満足度ではなく `replay-engine` の `hlog-1` で修正操作の回数を取る
（改善は不可視で誤りだけが可視、という非対称があるため聞いても測れない）。

### 4.5 マークの閾値

マークの適合率が低い（＝マークが多すぎる）と校正ツールとして機能しない。
理論的には決まらないので、実データのゲート性能から切る。

**`baseShare < 0.9`（λ=500）を既定にする。** マーク率 17.8%（6 文に 1 文）で
救えるケースの 88.2% を捕捉し、適合率は 63.5%（ベース誤り率 31.8% の 2 倍）。
0.99 まで緩めると適合率が 47.2% まで落ちてマークが多すぎになる（§4.2b）。

### 4.6 文長の分布（2026-09-21 実測）

**測ったときの問い**: 矩形の横幅と高さは「1 文が何文字か」で決まる。
**いまの問い**: 未確定スパンは常時どれくらいの長さになり、生ひらがなのまま打ち切る文はどれくらいか。
矩形は消えたが（§2.8）、**数字はそのまま両方の問いに使える**。本文コーパスから分布を取った。

コーパスは note.com の記事 **43 本 / 2,773 文**。スクリプトは
`logical-layout-labo/hechima-wasm/eval/corpus_lengths.py`。

> ⚠ **生成 AI が書いた文を混ぜてはいけない。** 目に見えて長く、幅の判断が広い側へずれる。
>
> | | 平均 | 中央値 | 幅 35 字で 1 行 |
> |---|---|---|---|
> | 本人（43 本） | 29.5 字 | **23** | 72.1% |
> | AI 主体（除外した 5 本） | 35.7 字 | **31** | 60.0% |
>
> 除外リストは `eval/excluded_notes.txt` にある。

**文長の分布**: 平均 29.5 字 / 中央値 23 字 / p75 37 / p90 57 / p95 74 / 最大 297。
右に長い裾がある。

インライン模型でこの分布がどう効くかは、この節の末尾にまとめてある。

| 幅 | 1 文が 1 行に収まる |
|---|---|
| 30 字 | 64.7% |
| 35 字 | 72.1% |
| **40 字** | **78.8%** |
| 45 字 | 83.0% |

30 → 45 字で +18pt しか伸びない。**広げても得が少ない**ので可読性側で切る。

**連続 3 文の合計行数**（2,687 組）—— 以下 (A)(B)(C) までは**矩形の高さを決めるための測定**で、
矩形が消えたいま（§2.8）**結論としては使わない**。数字そのものは残す
（`hlog-1` の読み替えや、将来また窓を持つ設計が出たときに効く）。

| | 4 行 | 5 行 | **6 行** | 7 行 |
|---|---|---|---|---|
| 幅 35 字 | 72.6% | 89.1% | 95.6% | 98.5% |
| **幅 40 字** | 81.8% | 92.8% | **97.6%** | 99.0% |

6 行が折り返し点。5 行では 3 文が収まらない場合が 7% 出る。

**かな長**（400 文を逆変換、全件成功）—— 1行欄の幅に効く。

`かな長 / 表記長 = 1.18`（中央値 28 かな / p90 63）。

| 1行欄の幅 | 1 文まるごとが残る（§2.3 の猶予） |
|---|---|
| 30 かな | 54.8% |
| 35 かな | 64.0% |
| **40 かな** | **72.2%** |
| 45 かな | 77.0% |

**溢れ方**（幅 40 字）—— 高さを固定する判断（§2.1）の根拠。

*(A) 1 文が単独で何行になるか*

| 行数 | 1 | 2 | 3 | 4 | 5 | 6 | 8 |
|---|---|---|---|---|---|---|---|
| 割合 | 78.8% | 17.3% | 3.0% | 0.65% | 0.07% | 0.14% | 0.04% |

**6 行を超える 1 文は 2,773 文中 1 文（0.04%）。**

*(B) 直近 N 文が 6 行に収まる率*

| | |
|---|---|
| **直近 1 文** | **100.0%** |
| 直近 2 文 | 99.5% |
| 直近 3 文 | 97.6% |

**直近 1 文が 100% というのがこの測定の要点である。** いま書いている文が窓から
隠れることは起きず、溢れて見えなくなるのは常に「いちばん古い確定した文」になる。
だから固定高でも壊れない（§2.3）。

*(C) 6 行の窓に実際に見える文の数*

| 3 文 | 2 文 | 1 文 |
|---|---|---|
| 97.6% | 1.9% | 0.5% |

可変高にすればこの 2.4% を救えるが、代わりに 100% の場面で高さが読めなくなる。
**割に合わないので固定にした**（§2.1）。

**旧案での結論: 幅 40 字 × 矩形 6 行・固定。** —— **この結論は §2.8 で破棄した。**

**インライン模型での結論**: 寸法は本文のレイアウトが決めるので、この測定から決まるものは無い。
代わりに残るのは**長さの見積もり**である。

- **未確定スパンは常時 70〜90 字**（表記長の中央値 23〜31 字 × 3 文）。
  OS ネイティブ版では preedit の長さそのものになる（§8.4）
- **句点まで画面に並ぶひらがなの量は「かな長」で見る**（表記長ではない）。
  中央値 **28 かな** / p90 **63 かな**。半分の文は 28 かな程度で変換されるが、
  1 割は 63 かなを超える —— **そこだけが「ひらがなの壁」**になる
- 裾（最大 297 字）は変わらず存在する。§2.3 の「句点で変換」は、
  **長い文ほどキャレットの飛距離が大きくなる**ことを意味する。未検証の懸念として置く

#### 外れた懸念（記録）

「note 記事は**推敲済みの公開文**なので、書き出した直後を扱うこの UI のコーパスとしてはずれる
（推敲を通った文は初稿より長い）」と当初考えたが、**外れた**。

| | 平均 | 中央値 |
|---|---|---|
| 日記・チャレンジ系（初稿寄り） | 28.9 字 | 23 |
| 記事系（推敲寄り） | 30.3 字 | 24 |

ほぼ差が無い。**公開記事を初稿の代理に使える。**
なお `replay-engine` の `hlog-1`（§7 の評価手段）なら初稿そのものだが、
記録はまだ存在しない。UI ができてから貯まるものである。

### 4.7 誤打の検出力（2026-09-23 実測）

§2.4(a) の「句点で踏みとどまる」案の材料。**誤停止が 1 割あれば、止める機能は成り立たない**ので、
拾う割合より先に「誤打のない文をどれだけ止めるか」を見る。

スクリプトは `logical-layout-labo/hechima-wasm/eval/typo_eval.py`（labo #805。50 秒で再現できる）。

**方法**: note の本人記事から 1313 文を取り、読み → ローマ字の打鍵列 → **誤打を 1 つ入れる**
（QWERTY の隣接キー置換 / 脱落 / 隣接キー挿入 / 入れ替えを等確率）→ 配列エンジンと同じ規則
（`sequential-buffer.ts` の `resolve` を移植）でかなに戻す。誤打あり・なしの両方に検出器を当てる。
英字の語・括弧は打鍵をそのまま通し、誤打の対象にしない。

| 検出器 | 拾う | 誤って止める |
|---|---|---|
| **かなにならずに残った打鍵**（強いマーク） | **52.4%**（位置も全件合う） | **0%** |
| ＋ 日本語に出ないかなの並び（`とぁ` 等） | 54.8% | 0.1% |
| ＋ 細切れの文節（≤2 かな × 3 連） | 60.4% | 9.0% |
| 細切れの文節（≤2 かな × 2 連）単独 | 52.4% | 28.9% |

- **強いマークは読みの英字ではなくエンジンで取る**（§2.4(a)）。最初に読みの英字で測ろうとして、
  本文の英字（`IME` / `azooKey`）を誤打に数えかけた
- 英字の区間が 2 つ以上に割れた文は 688 件中 **0 件**。「どれに吸い付くか」はほぼ問題にならない
- 英字の右端から BS するだけで直るのは 64%。右にさらに 1 かな壊れているのが 19%、2 かなが 16%
- 残りの 45% は 1〜2 かなが**別の正しいかな**になったもの。経路コスト（1 かなあたり）での
  識別力は AUC 0.667（§4.2b の「base が正しいか」0.677 と同じ水準）

**限界**: 誤打は合成である。実際に句点まで残る誤打は、英字が打鍵中の表示に見えて直されやすい分、
**「別の正しいかな」の側へ寄っているはず**で、52% は上限寄りに読むこと。
本人の誤打の実分布は `replay-engine` の `hlog-1` を集めれば取れる。

### 4.8 区切りの揺れの印はふだんの文章で何文に付くか（2026-09-25 実測）

§4.2b の「6 文に 1 文」は evaluation.tsv（既知の難例の回帰セット）での値で、ふだんの文章での割合ではない。
印は書き手を止めうる（§8.8）ので、本人の note 記事 1301 文で測り直した。
スクリプトは `logical-layout-labo/hechima-wasm/eval/mark_rate.py`（labo #809。60 秒）。

**原文（本人が実際に書いた表記）を正解**にできるのがこの測定の強みで、印が役に立つ文
（B = base が原文と違い、別の区切りの経路が原文と一致する）も数えられる。

| しきい値 | 印が付く文 | 印のうち B | B の捕捉 |
|---|---|---|---|
| 0.7 | 9.2% | 15.0% | 18/39 |
| 0.8 | 14.5% | 14.4% | 27/39 |
| **0.9**（いまの値） | **22.5%** | **9.9%** | **29/39** |

- **印は 4〜5 文に 1 文付き、役に立つのはその 1 割。** 残りの 9 割は区切りを変える必要の無い文である
- **長い文ほど付く**（よみ 80 かな以上で 51%）。経路の数が文の長さで増えるので、base の取り分が薄まる。
  baseShare は文全体の量なので、長さで割り引いていない
- B（区切り違いで救える文）はふだんの文章で 3.0%。回帰セットの 5.8% より少ない
- **B は文全体の一致で見ているので下限寄り**。区切り違いを直しても、同じ文の別の語が原文と
  違えば B にならない。長い文ほど効く

**閾値は未決。** 0.9 は回帰セットで「捕捉 88%」を取るために選んだ値で、ふだんの文章では印が多すぎる
おそれがある。ただし印は背景を塗るだけで書き手を止めないので、多すぎることの代償は §2.4(a)
（止める）より軽い。実地で「うるさいか」を見てから決める。

## 5. 将来の拡張点

### 文をまたぐ判断は Mozc には原理的にできない

Mozc の変換単位は実質 1 文で、Viterbi も文内で閉じている。
したがって 3 文バッファを持っても、**Mozc だけでは 3 文分の文脈を精度に使えない**。

3 文保持の根拠は現状こうなっている。

- (a) 文脈を使って精度を上げる … **Mozc では満たせない（空席）**
- (b) ユーザーが 3 文を見渡して校正できる … 成立
- (c) FIFO を滑らかに回す … 成立

(b)(c) だけで 3 文保持は正当化されるが、(a) は空いたままである。

### 空席の埋め方（現時点では実装しない）

文全体・複数文を見た上での判断を外部モデルに委ねる余地がある。
標的を絞るなら **「1位経路と2位経路が区切りで食い違い、かつコスト差が小さいケース」**
が最も条件が揃う。選択肢の重なりが小さく、体感インパクトが大きく、現在の UI では救えない領域である。

ただし現時点では**実装しない**。理由:

- オフラインで動くこと（IME としては大きい）
- レイテンシがゼロであること
- UI と測定を先に済ませ、Mozc のマージンだけで実用になるかを見てから判断できること

外部モデルを使う場合の設計上の注意（先に書いておく）:

- **各文節を独立に選ぶと、全体として破綻した系列が出る**（marginal argmax ≠ joint argmax）。
  経路単位で選ばせるか、分布を Mozc のコストと合成して Viterbi を回す
- **候補にない語は選べない**。カバレッジは常に辞書側の問題として残る
- **選択肢の重なりが大きいと分布が割れる**。表記ゆれを選ばせてはいけない
- **出力は論拠であって結論ではない**。合成（重み・閾値）はコード側に明示的に置き、
  生の判断は再利用可能なまま保つ。Mozc の `cost` が陥っている状態を繰り返さない

### 4a'' に入るときの前提（インライン版）

- **未確定は preedit ではなくホスト側の描画で作る**（`site` 版）。`site/src/app.ts` は既に
  「未確定はカーソル位置にインライン挿入（標準 IME の見た目）」で動いているので、
  同じ仕組みを 3 文ぶんに広げる形になる
- **Space と Enter の割り当ては決まっている**（2026-09-22）。
  Space = 空白を入れる（マークの上でだけ候補を出す。§2.6）、
  Enter = 一段ずつ剥がして確定（§2.3 の表）。**どちらも空振りさせないこと** ——
  IME に見せる以上、押して何も起きないのは「壊れている」と読まれる
- **コンポーザが持つキーは三つだけ**（§2.6 の表）。空白 = Space / 文を区切る = 変換キー（JIS）/
  確定 = Enter。**どれも役として持ち、物理キーは配列ごとに割り当て直せる形**にする
  （新配列では Space も変換キーも配列側に取られうる）
- **「文を区切る」は句点と同じ経路に落とす**（§2.3）。句点の処理と分岐を増やさない ——
  `flow.ts` の句点切り出しに、文字を伴わない入口を一つ足すだけで済む
- **変換は句点で 1 回。ライブ変換は持たない**（§2.2）。打鍵ごとに `convert` を呼ばない
- **後続の文が前の文を変換し直すことはない**（§2.3 / §5）。後から変わるのはマークだけ
- 未確定スパンは常時 70〜90 字になる（§4.6）

### 4b に入るときの前提

**順序は「かなカーソル → 走査の器 → マークの中身」になった**（2026-09-23）。
器があればマークは差し込めるが逆は成り立たず（§2.4）、
**その器はかなカーソルの上にしか建たない**（到達しても直せないため。§2.4「到達しても直す手段が無い」）。

**同梱している wasm の実体**（2026-09-23 に確認。`VENDOR.md`）:

## 8. 検討事項（2026-09-21 の雑談と実地から）

**8.1 を除いて、ここは仕様ではない。** 後から効きそうな論点の記録である。

**8.1（一貫性の台帳）だけは採用を決めて §2.4 に反映した。** 残りは未決のまま。

### 8.1 文書内の一貫性の台帳（仕様に採用済み・2026-09-21）

> **この節は §8 の他の項と違い、決定済みである。** §2.4 に反映した。

§2.4 は当初「表記ゆれには正解がないからマークしない」としていた。基準を取り違えていた。

人が表記ゆれについて不満に思うのは「どちらが正しいか分からない」ではなく
**「同じ文書の中で揺れている」**ほうである。そして**一貫性には文書の中で確定した答えがある**。
校正ツールの表記ゆれチェックも、正誤ではなく統一を見ている。

> `content_key → この文書で選ばれた content_value` の小さな台帳を持ち、
> 次に同じ content_key が来たら**マークに使う**

**記憶を持たないので汚れない。** 学習ベースで表記ゆれを揃えると「3 週間前に一度そう確定した」
が延々と残るが、文書内の先例なら文書が変われば消える。**自己洗浄される。**
「学習をしない」というより**「文書の寿命で消える学習にする」**。

**並べ替えには使わない（§2.4）。** 台帳で候補順を変えると「現在の文」で静かに効き、
意図的な使い分けを黙って壊す。実例は §4.2d の `ともだちのしんちょうをはかる` で、
`はかる` は 図る / 測る / 計る / 量る が同じ content を共有する。
マークに限れば §2.4 の「書き換えずマークする」方針のままなので、使い分けは壊れない。

#### content_key はそのままでは使えない（2026-09-21 に実測）

当初「活用が違っても content で一致する（『観た』も『観る』も content_key は「み」）」と
書いていたが、**これは誤りだった**。Mozc の `content_key` / `content_value` は
「活用形から付属語を除いたもの」であって、語幹ではない。

| 入力 | `ckey` / `cvalue` |
|---|---|
| みる | **みる / 見る** |
| みた | み / 見 |
| はかる | **はかる / 図る** |
| はかった | **はかっ / 図っ** |
| うれしかった | うれしかっ / 嬉しかっ |
| かいせつする | かいせつする / 解説する |

生の `content_key` で引くと、**図る と 図った が別の棚に入る**。台帳の主目的が成立しない。

**正規化が要る。** `content_value` 末尾のひらがな連を落とし、`content_key` からも同数だけ落とす。

```
図る  → はか/図     図った → はか/図     図ります → はか/図
見る  → み/見       見た   → み/見       見ている → み/見
嬉しい → うれ/嬉     嬉しかった → うれ/嬉
解説  → かいせつ/解説  解説する → かいせつ/解説
取り消し → とりけ/取り消  取り消した → とりけ/取り消
```

19 の活用形で検証し、全部同じ棚に落ちた。言語的に正しい語幹である必要はない。
**同じ語が同じ棚に落ちればよい**（`取り消し → 取り消` は語ではないが、一貫していれば足りる）。

**全部かなの候補は台帳に入れない**（落とすと空になる = 統一すべき表記を持たない）。

留保: わざと使い分けることはある（「見る」と「観る」を意味で分ける等）。
§2.4 の**書き換えずマークする**方針のままなら、揺れを指摘するだけで意図的な使い分けを壊さない。

#### 層の大きさ（測定済み）

C1 の 61 件中 12 件（19.7%）が表記ゆれで、うち 2 件は `そけんのらんよう` /
`こうそけんのらんよう` の `乱用 / 濫用` —— まさに台帳が想定している形である（§4.2d）。

ただし台帳の価値は「表記ゆれの発生率 × 文書内で同じ棚が再出現する率」であり、
**後者は単文の評価セットでは測れない**（§4.2e）。**測らずに採用すると決めた。**
機構がモデルを要さない表引きで（§8.5）、外しても文書の寿命で消え、
§2.4 の方針上マークしか出さないので、失敗のコストが小さいためである。

#### エンジン側（実装済み）

`hechima-wasm` v0.15.0 で `ckey` / `cvalue` を返すようにした（labo #801）。

- `hechima_convert` / `hechima_convert2` … 候補と並走する `ckeys` / `cvalues`
- `hechima_paths` … 各文節の `ckey` / `cvalue`

なお**正規化を通すと `key` / `value` から直接引いても同じ結果になる**（実測）。
`ckey` / `cvalue` は Mozc 自身の自立語判定であって、便利ではあるが必須ではない。
正規化はホスト側（方針側、§8.2）が持つ。**エンジンには混ぜない。**

### 8.2 台帳は 3 文バッファとは別物（寿命が違う）

混同しないこと。

| | 正体 | 寿命 | どこが持つか |
|---|---|---|---|
| **3 文バッファ** | 変換の先読み窓 | 文の数本 | state（モデルに渡す） |
| **一貫性の台帳** | `content_key → content_value` | 文書 | **方針**（コードが持つ） |

窓を伸ばして台帳を兼ねさせるのは筋が悪い。コストが線形に増えるうえ、遠い文は変換の文脈としては
ノイズになる。そして台帳は**方針側**なので、Mozc のコストにも外部モデルの分布にも混ぜない
（混ぜた瞬間に §3 の `cost` と同じ「後から分離できない」状態になる）。

### 8.3 「といった / と言った」は表記ゆれではない

「と言った」は動詞、「といった」は連語。**読みが同じだけの別語**で、分類としては
「解説する / 開設する」と同じ棚（意味の問題）。境界は**同じ語か、別の語か**。

ただし**一貫性の規則はこの区別を要さない**。「この文書で既に解説と書いた」も次の
「かいせつ」への妥当な事前確率である。区別が要るのは**マークの出し方だけ**
（表記ゆれ = 揺れているときだけ / 同音異義語 = 迷っているときだけ）。

### 8.4 OS ネイティブ版 — インライン模型で裏返った（2026-09-22 改訂）

§6 で「OS 全体での動作は後で考える」とした件。旧案（矩形オーバーレイ）でも成立しそうだと
書いていたが、**インライン模型に移って前提が裏返った。**

| 論点 | 旧案（矩形）の答え | インライン模型の答え |
|---|---|---|
| キャレット位置 | 中央固定（案 A）で問題を回避 | **要らない**（本文の中に描くので）。候補窓の位置だけはプロトコルが運ぶ |
| アプリとの協調 | **空の** preedit で composition 状態だけ立てる | **preedit に中身を入れる。** これがプロトコル本来の使い方 |
| 文書境界を知れない | 時間（30 分程度）＋ ウィンドウ/アプリで近似 | 同じ（変わらず） |
| UNDO の粒度 | FIFO なので一文単位 | 同じ（変わらず） |

**旧案の「preedit は空にすること」は回避策だった。** 中身を入れるとアプリがインラインに描いて
二重表示になるから空にしていた —— つまり**アプリがインラインに描くこと自体は正常な挙動**で、
旧案はそれを避けるために矩形を自前で描いていた。インライン模型はその描画をアプリに任せる。

**新しく出る懸念: preedit が長い。** §4.6 のとおり未確定スパンは常時 70〜90 字になる。
通常の IME の preedit は 1 文節〜1 文なので、この長さは前例が少ない。
再レイアウト・スクロール追従・アプリ側の preedit 長制限で挙動が割れる可能性がある。
**未調査。** 実機で確かめるまで「乗る」とは書かない。

なお旧案の副産物「OS 版は案 A 一択なので案 A の実使用データが自然に取れる」は、
配置そのものが消えたので無くなった（§4.4）。

### 8.5 ここまでの改善に外部モデルは要らない

記録として。§4 までに挙げた改善のうち、モデル呼び出しを要するものは無い。

| 改善 | 必要なもの |
|---|---|
| 区切り違いの提示 | ラティス |
| マークの判定 | Mozc 自身の経路コスト |
| BS で分節が壊れない | ステートレス再計算 |
| 打鍵タイミング由来の揺れ | 流し込み単位での変換 |
| 誤打マーク | 配列エンジンの「かなにならなかった打鍵」の印（2026-09-23。細かい分節は退けた） |
| 文書内の表記統一 | content_key の台帳（8.1） |
| 学習の文脈分離 | 文書スコープ |

例外は**候補選択の精度そのもの**（§4.2c の 16.8 ポイント）。これは構造では直らず、
純粋に判定器の質の問題で、外部モデルが働くとしたらそこ。ただし日本語で Mozc の n-gram より
強いかは**誰も測っていない**。

理由ははっきりしている。**不満の多くは知能の不足ではなく構造の制約だった。**
BS で壊れるのは状態を持っているから、区切り候補が出ないのはワイヤフォーマットに乗らないから、
表記が揺れるのは記憶のスコープが文書に合っていないから。どれも知能はボトルネックではない。

### 8.6 候補ポップアップは「意味」も運べていない（§1 のもう一つの面）

§1 は「プロトコルが**区切りの違う候補**を運べない」と書いた。同じ切り口には**もう一人の犠牲者**がいる。
**候補の意味**も運べていない。

エンジンは各候補が何者かを知っている —— `cost` / `wcost` / 品詞（`lid`,`rid`）/ `content_value` /
`attributes` / 出自（辞書か、学習か、rewriter が差し込んだ日付・記号・単漢字か）。
ところが `CandidateWindow.Candidate` に乗るのは実質 `{index, value, id}`、
**文字列と順番だけ**。だから UI は順位しか描けない。

**不満の正体は「注意の配分ができない」ことだと思われる。**

- 候補がコイン投げ状態なら、よく読む必要がある。だが UI はそれを教えない
- 候補が確信を持っているなら、見ずに確定してよい。だが UI はそれも教えない
- 結果、**どちらであっても毎回同じだけ目で追う**

誤変換そのものより、この「いつ注意を払うべきか分からない」ことのほうが日常的な消耗としては
大きい可能性がある。これは §4.2b の**較正と識別力の問題の UI 版**でもある ——
分布を持っているのに順位に潰して見せており、潰した時点で
「この順位に意味があるのか」が失われる。

**この UI の設計は、既にこの不満への答えになっている。** マークは「ここを見ろ」という信号で、
注意の配分を機械に肩代わりさせるものである。§1 は「区切りを提示できない」から出発したが、
「どこに注意を向ければよいか分からない」から出発しても同じ場所に着く。

部品も一部ある。候補の二層化（`WireSegment.costs` / `hechima-wasm-cost/`）は
「コストを UI まで運ぶ」配管そのもので、別の目的で作られたものがここで意味を持ち直す。

留保: **情報を増やせばよいわけではない。** 全候補に確信度バーと出自タグを付けたら、
注意配分のヒントを読むために注意を払うことになる。答えは「候補ごとに情報を足す」ではなく
**「分布の形が問題になるときだけ出す」** —— つまり、やはりマークである。

### 8.7 ~~概念の学習コスト — どこに寄せるか~~ ✅ 決めた（2026-09-22。IME に寄せる）

器（§7 の 4a）を打ってもらった結果、**いちばん強く出たのは精度でも配置でもなかった。**

> アプリの概念が新しすぎて、慣れるまでが難しい。何らかのアナロジーや、
> 類似アプリに寄せる判断をしないと、**使えなさそうと初手で評価されそう**。

これは §1（なぜ作るか）に対する反証ではない。§1 は「プロトコルの制約で区切り違いが出せない」
という構造の話で、そこは変わらない。**出てきたのは、構造の正しさが体験の入口を保証しない、
という別の層の問題**である。

#### 寄せ先の候補は二つある。同じものではない

| 寄せ先 | 何が対応するか | 何に効くか |
|---|---|---|
| **ターミナル**（プロンプト行 + スクロールバック） | 1行欄 = プロンプト / 矩形 = 直近のスクロールバック / ホスト = その先 | **運動**。行が上へ送られるのが見えるから、画面外へ出たものが失われていないと分かる（§2.3 の穴に直接効く） |
| **既存 IME の未確定表示** | 矩形 = 未確定表示を本文から切り離して大きくしたもの | **初見の説明**。案 B はこの見え方そのものになる（§4.4 の第一軸） |

**構造が一致するのはターミナルのほう、初見の納得が得やすいのは IME のほう。**
三層（打つ場所が最下行に固定 → 上へ流れる → その先に本体がある）が素直に対応するのは
ターミナルだが、日本語入力として初めて見る人が持っている参照枠は IME である。

#### 決定（2026-09-22）: IME に寄せる。ただし「寄せる」ではなく「戻す」

**IME を選んだ。** ただし決まったのは表面の見た目ではなく、**UI の構造そのもの**だった。

寄せ先を IME にすると、矩形を「IME の未確定表示に似せる」のではなく、
**本当に IME の未確定表示にしてしまう**のがいちばん筋が通る —— 本文の中に直接描き、
打鍵中はひらがな、句点で変換、4 文目で確定。ここまで来ると矩形を置く場所が無くなる。
これが §2 の全面改訂（§2.8）につながった。

**ターミナル側の利点（運動が見える）は、捨てたのではなく不要になった。**
運動が要ったのは「矩形の中と外で場所が違う」からで、インライン模型ではテキストが動かない。
確定は下線が消えるだけである。ただし**穏やかすぎて気づかない**可能性は残るので、
§4.4b の成立条件に入れてある。

#### 実地で機能した（2026-09-22。4a'' を実機で試した）

旧模型（矩形）の report は「アプリの概念が新しすぎて、慣れるまでが難しい。
**使えなさそうと初手で評価されそう**」だった。インライン模型の report はこうなった。

> **標準 IME みたいな手触りだね。** 変換のつもりでスペースキーを押すと空白が入るのが
> ちょっと不思議だけれど、それ以外はそんなに変じゃない。

**この節が立てた問題は解けた**と見てよい。残っているのは「ちょっと不思議」一点で、
それは §2.6 が意図して破った反射そのものである —— **学習コストの問題が、
設計上の既知の代償一つにまで縮んだ**。

**代償**: IME に見えるものには IME の期待が来る（§2.6）。
Space と Enter に何をさせるかが新しく問題になった —— **寄せ先を選んだことの裏側**であり、
この決定で消えた問題ではなく、この決定が生んだ問題である。
2026-09-22 に決着した（§2.6 / §2.3）が、**IME の反射のうち「Space = 変換」だけは破っている。**
緩和は「空振りしない」ことで、押すと空白が入るので一度で分かる。

#### 「慣れれば分かる」で押し切らない

この UI の動機は精度ではなく、**候補ポップアップでは原理的に直らない 18.3% を可視化すること**
だった（§4.2b）。可視化が伝わらなければ、動機そのものが成立しない。
「慣れの問題」に分類した時点で、測るべきものが測れなくなる。

#### 学習コストは「比較の前に塞ぐもの」だった

配置の比較（§4.4）は、学習コストが交絡している間は差が埋もれる。
この節を塞ごうとした結果、**比較の対象そのものが消えた**（§4.4 → §4.4b）。
以後、比較には成立条件を先に書く。

### 8.8 これは IME ではなく「思考を書き連ねる」道具かもしれない（2026-09-22・実地）

4a'' を実機でしばらく使った report が、途中で変わった。

> 入力中に Shift を押してアルファベットを入力する、とかまで IME そっくりです。
> ちょっと書いてみたら、**これは IME なんかではなく「自動変換を信じて多少の変換ミスを
> 許容しつつ、思考を書き連ねるのに最適っぽい」**という印象に変わりつつあります。

**最初の印象（IME そっくり）は §8.7 の狙いどおりで、二つ目の印象はその先にある。**
寄せ先を IME にしたのは学習コストを下げるためだったが、
同じ決定が**別の性質**を連れてきていた。

#### 何がその性質を作ったか

**止まる理由が無くなっている。** 変換キーを押さない・候補を選ばない・確定しない。
句点を打てば勝手に変換され、4 文目に入れば勝手に確定する。
**手を止める操作が一つも要求されない。**

これは §1 の動機（区切り違いを可視化する）から出たものではなく、
**キーの割り当て（§2.6）の副産物**である。Space を空白に戻し、変換を句点に渡した結果、
「変換のために打鍵を止める」という日本語入力の基本動作が消えた。

なお §2.4 には既に「思考の速度で書き出すことが目的であり、表記の精密さは後工程に委ねる」
と書いてあった。**書いてはあったが、動機としてではなく表記ゆれを許容する理由として書いていた。**
実地はそれを主題の側へ引き上げた。

#### 新配列と相性がよい理由は、単なる親和性ではない

report は「新配列と組み合わせたらもっと楽しそう」「新配列作者のよく言う
**『思考をストレスなく記録する』**ツールになりそう」と続く。これには具体的な裏付けがある。

**§2.6 で破った唯一の反射（Space = 変換）が、新配列使用者には最初から無い。**
新配列は Space を同時打鍵のシフトに使うことが多く（`naginata.json` は `space+Q` のように
`space` をシフト群に持つ）、**Space は配列エンジンに食われてコンポーザまで届かない**。
つまり彼らの変換キーはもともと Space ではない。

**残っている唯一の代償が、いちばん相性のよい層では初めから発生しない。**

#### 4b（マーク）がこの手触りを壊しうる

**警告として書いておく。** いまの心地よさには、**直す手段が無いこと**も効いている。
マークも候補選択も無いので、そもそも止まれない。

§2.4 のマークは「ここを見ろ」という信号で、注意の配分を機械に肩代わりさせるものだから、
方向としては矛盾しない。だが実装の仕方によっては**止まる理由を作り直す**ことになる。
4b では「この UI は書き手を止めるか」を判断基準に加える ——
§4.4b の比較に載せるべき軸でもある。

### 9.2 ~~λ を「較正する」と書いたのは言葉が間違っている~~ ✅ 解消（2026-09-21・名前を決めた）

§4.2 (1) は当初「λ は評価セットで**正解率に対して較正する**」と書いていた。
第 1 回はこれを「AUC 0.585 でほぼコイン投げだから較正の的が無い」と否定したが、
**その 0.585 も汚染された採点の産物だった**。訂正後は次のとおり。

| | 第 1 回（汚染あり） | 訂正後 |
|---|---|---|
| AUC（base が誤りか） | 0.592 | **0.677** |
| 較正表 | 単調でない | **単調** |

**「情報が入っていない」は言い過ぎだった。** 等調回帰などで較正する的は一応ある。

それでも名前は付け替えた。P≈1.0 で実際の正解率は 78.6% であり、
「base が正しい確率」としては読めない。一方「救えるケースか」に対しては AUC 0.889 で効く。
**計算しているものと効いている対象がずれていて、`P(base)` は前者を確率のふりをした名前で
呼んでいた**、というのが問題の形だった。

**決定（2026-09-21）: 量は計算の名前で呼び、解釈はゲートの名前に持たせる。**

| | 名前 | 何を言っているか |
|---|---|---|
| 量 | `baseShare(paths, lambda)` | 列挙した経路の重みのうち base の区切りが占める**取り分**（0..1） |
| 判断 | `shouldOfferAlternatives(s) = s < 0.9` | 代替を出す価値があるか。**AUC 0.889 が付くのはこちら** |
| つまみ | `lambda`（λ=500） | ソフトマックスの**温度**。較正パラメータではない |

- **`P(...)` と書かない。** 取り分は列挙分（`max_paths=60`・区切りあたり最大 32 本）の
  重みの総和に対する割合であって、全経路の確率でもなければ正解確率でもない
- **量の側に「代替価値」という判断の名前を付けない。** 上の 2 案のうち後者
  （的を「救えるケースか」に変える）は実態に合っているが、それは**ゲートの意味**であって
  量の意味ではない。§8.1 の一貫性の台帳がマークのもう一つの根拠として入ってくるので、
  判断を量の名前に焼き付けると、台帳が入った時点で名前が嘘になる
- **向きは base 側のまま**（小さいほどマーク）。§4.2b / §4.5 の閾値表はそのまま生きる

較正そのものは**やらない**。等調回帰の的はあるが、必要なのは順位だけで、
較正済みの絶対値が要るのは Jev の分布と足すとき（§5）だけであり、それは実装しない。
