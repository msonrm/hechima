## 1. なぜ作るか

### 文節 UI は解空間の損失のある射影になっている

Mozc（を含む現代のかな漢字変換）は、入力文字列に対してラティスを組み、
**単語の選択と区切りの決定を一つの最小コスト経路問題として同時に解いている**。
ありうる区切り方は最初から全部ラティスの中に同居していて、経路探索で一本に絞られる。
文節境界は `Segmenter`（品詞IDペアのビット配列）が経路の品詞列から規則的に導くだけで、
独立に選ばれているわけではない。

ところが UI は、この一つの同時選択を「境界を動かす」「候補を選ぶ」という
二つの逐次的な局所選択に因数分解している。この因数分解には正当な理由がある
（5文節×3候補＝243通りの経路に、5回の局所選択で到達できる。相互作用空間の指数的圧縮）。
しかし損失もある。

**1位経路と2位経路が区切りで食い違っているとき、候補ポップアップは原理的に無力**である。
いくら候補を選んでも直らない。ユーザーは「これは候補の問題ではなく区切りの問題だ」と
自分で診断してから、別の操作（境界の伸縮）に切り替える必要がある。
その診断のコストがユーザーに押し付けられている。

### 制約はエンジンではなくプロトコルにある

この制約は変換エンジンの限界ではない。`immutable_converter` は N-best 経路を既に計算しており、
区切りの違う候補は**エンジンの中に存在している**。出せないのはプロトコルの形式のせいである。

Mozc のプロトコル定義（`protocol/commands.proto`, `protocol/candidate_window.proto`）では、

- `Preedit.Segment` … 文節が `UNDERLINE` / `HIGHLIGHT` 付きでワイヤに乗り、**アプリ側が描画する**
- `CandidateWindow.Candidate` … 候補は `value`（文字列）＋ `index` のみ。
  候補ウィンドウは `position`（合成文字列内の文字位置）に紐づく

つまり**候補は「合成文字列のある位置を置き換える文字列」としてしか表現できない**。
区切りを変える候補はこのフォーマットに乗らない。IME 単体で変えられる話ではなく、
プロトコルとそれを描画する全アプリケーションの問題になる。

これは歴史的な経緯でもある。初期のかな漢字変換は**単文節変換**で、区切るのはユーザーの仕事だった。
文節ごとの候補リストは、その時代には完全に正しい設計である。その後、連文節変換で機械が境界を
推定するようになったが、UI とプロトコルは残った。

### hechima はプロトコルの外にいる

hechima は入力・キーマップ・変換・表示の 4 つの箱をページの中に持っている。
**preedit も候補ウィンドウも OS に渡さない**ので、この制約は構造的に存在しない。
ホストに渡すのは確定済みの文字列だけでよい。

**エンジンはもう答えを持っていて、出す道がないだけ**という状況なので、
道を作れば区切り違いの並列提案が成立する。

## 2. UI 仕様

### 2.1 全体の形

テキスト入力にフォーカスがある状態で、ホットキーにより出現する矩形オーバーレイ。

```
┌──────────────────────────────┐
│                              │
│   確定した文（固定・マーク可）      │  ← 矩形（大部分）
│   確定した文（固定・マーク可）      │
│   現在の文（変換済み・書き換わる）   │
│                              │
├──────────────────────────────┤
│  …ひらがな入力中          ▍  │  ← 1行欄（キャレット右端固定）
└──────────────────────────────┘
              ▲ ホストのキャレット
```

読み方の役割分担:

- **1行欄は「監視」** — 自分が今打ったものの確認。日本語の読み方向とは逆（右端固定・左へ流れる）
  なので読解には向かないが、内容は自分が打ったものなので読む必要が薄い
- **矩形は「読解」** — 通常の左→右。直したくなったときに視線を送る

### 2.2 三層モデル

| 層 | 中身 | 変換 | 書き換え | マーク |
|---|---|---|---|---|
| **1行欄** | ひらがな | **しない** | – | **誤打のみ** |
| **矩形・現在の文** | 変換済み | する | **する**（区切りも含め都度再検討） | しない |
| **矩形・確定した文** | 変換済み | 済 | **しない** | **変換の不確実性** |

この三層が設計の中核である。

**1行欄を変換しないことが、打鍵フィードバックのセーフガードになっている。**
ユーザーは常に誤打を意識しており、直近数文字が正しく打てているかを気にしている。
キャレット直近で自動変換が起きるとそのフィードバックが死ぬ。
1行欄がひらがな専用である限り、キャレット直近は**構造的に必ず生ひらがな**になる。
「そんな直近では確定度が出ないから大丈夫」という確率的な期待に頼らず、設計として保証する。

**書き換えが「現在の文」に閉じることで、揺れの収束が保証される。**
ライブ変換の要領で先頭から漢字になっていくが、後続の入力によってより良い候補があれば
置き換わる。区切り位置も都度再検討されるので、最適な区切りが適用されていく。
ただしこの揺れは現在の文の中だけで起き、確定した文には波及しない。

**確定した文は書き換えず、マークで伝える。**
後から「1文目のあれは違うかもしれない」と分かっても、自動修正はしない。
表示は安定したまま、情報は失われず、直すかどうかはユーザーが決める。

### 2.3 テキストの流れ

```
打鍵 → 1行欄（右端キャレット固定・左へ流れる）
     → 左端に到達した分から順に変換され、矩形へ
     → 句点の「次の文の1文字目」で、句点までが一気に矩形へ／1行欄クリア
     → 矩形は最新3文を保持。4文目に入ると最古の文がホストへフラッシュ（FIFO）
```

**句点そのものではなく、次の文の1文字目をトリガーにする。**
句点で即座に流すと、直前に打った数文字がフィードバックを受ける時間がゼロになる。
一つずらすことで、句点を打った直後に手を止めれば**文全体がひらがなのまま1行欄に残って見える**。
最終確認の機会が生まれる。打ち続けるなら次の文字と同時に流れるので、体感は変わらない。
止まった人にだけ見える猶予。

**3文保持の根拠。** ユーザーが見渡して微視的な校正を行える範囲がおおよそ3文であること、
および FIFO を滑らかに回すこと。それ以上の大きな校正はエディタ側の役割である。
なお「文脈を使って変換精度を上げる」という動機は Mozc では満たせない（§5 参照）。

**確定操作は持たない。** Enter は改行と衝突するし、明示的な確定はノールック入力の思想に反する。
編集可能な窓が後ろに滑っていくモデルとする。流れた後に気づいた誤りは、ホスト側で普通に直せばよい。

### 2.4 マーク

マークは二系統ある。混ぜない。

#### (a) 誤打マーク — 1行欄のみ

ローマ字入力は 1 モーラに複数打鍵を要するため、かな入力より誤打の機会が多い。
**「文がおかしいから直す」から「機械的にマークされた箇所を見る」への転換**は、
高速入力時の認知負荷を大きく下げる。変換前に検出できることに質的な意味がある。

検出は二段構え:

1. **ラティスの穴**（強いマーク） — どの語ともマッチしない読みの並び。
   `ka` → `ks` のように、そもそもかなにならない打鍵。確実だが範囲は狭い
2. **異常に細かい文節分割**（弱いマーク） — 1〜2文字の文節が連続する箇所。
   `ka` → `ki` のように「別の正しいかな」になってしまった誤打は 1 では拾えないが、
   語が壊れるため分割が細切れになる。範囲は広いが誤検出もある
   （固有名詞・未知語でも細切れになる）。閾値は実データで決める

#### (b) 変換の不確実性マーク — 確定した文のみ

**現在の文には出さない。** まだ入力が完了しておらず、不確実なのは当然だからである。
書き換わる最中のものにマークを付けても、1行欄と同じく視覚ノイズにしかならない。
既存のライブ変換が与える「過剰にがちゃがちゃ動いて目障り」という印象は、
未完了の状態を逐一表示に反映してしまうことが要因の一部であり、そこを踏まない。

対象は**意味が変わるものだけ**に限る。

- **区切りの揺れ** — N-best 経路が区切りで食い違っている
- **同音異義語** — 「解説する / 開設する」のように意味が違うもの

**表記ゆれはマークしない。** 「見る / 観る / 視る」「とき / 時」は意味がほぼ同じで、
正解が一意に定まらない領域である（Mozc の `oss.tsv` が部分制約でしか書けていないのと同じ理由）。
このツールは表記ゆれを**許容する**立場を取る。思考の速度で書き出すことが目的であり、
表記の精密さは後工程（エディタ側の校正）に委ねる。
マークが多すぎる校正ツールは誰も見なくなるので、ここは厳格に絞る。

表記ゆれの統一が必要な場合は、確率ではなく**方針**の問題としてユーザー設定で決め打ちする
（「『とき』はひらがな」等）。エンジンに聞くものではない。

#### マークへの到達

文字単位でキャレットを戻すとマークを探す作業自体が負荷になるため、
**次のマークへ / 前のマークへ**という線形走査を用意する。
マークがゼロになったら走査が終わる、という状態が分かりやすい。

1行欄のマークと矩形のマークは意味が違う（前者は打鍵の異常、後者は変換の不確実性）ので、
見た目も分ける。

### 2.5 候補の提示

マーク種別ごとに提示物が異なる。

**区切りの揺れ** — N-best 経路を**区切りでグループ化**し、各グループの最良経路を代表として提示する。
区切りを抽象的に見せてもユーザーは選べないので、実際の文を読ませる。

```
① ここで|履物|を|脱ぐ
② ここでは|着物|を|脱ぐ
```

区切りの異なる経路どうしは見た目がはっきり違うため、選択肢としての重なりが小さい。
これは細部だけが違う経路を並べる場合と対照的で、この UI が区切りを標的にする理由の一つでもある。

**同音異義語** — 該当文節の候補リスト。

**漢直・新配列との統合（任意）** — マーク箇所に対して候補リストだけでなく
「その字の打ち方」をガイドに出せば、選択ではなく直接入力で直せる。
漢直使用者には候補を探すより速い場面がある。`replay-engine` のキーボード図 SVG
ビジュアライザを流用できる。

### 2.6 配置と表示制御

**配置は未決。二案を実装して実地で比べる。**

| 案 | 利点 | 懸念 |
|---|---|---|
| **A: 画面中央固定** | タイプライタースクロール的に視線が固定される。微視的な推敲が常に同じ場所で行われる安心感。キー入力ガイドの位置が安定する | ホストのキャレットと離れ、確定した文字列が視界の外へ流れ込む。短文入力には大げさ |
| **B: ホストキャレット追従** | 既存 IME のメンタルモデルに近い。エディタ側の推敲に移るときの視線移動が小さい | 入力位置ごとに場所が変わる。上に余裕がなければ下に出すしかなく、本文を覆う |

**案 B を採る場合は、キャレットの上に出す。**
ブロックの構成が「矩形（上）＋1行欄（下）」であることが効く。

- キャレットの**下**に置く → キャレット → 矩形 → 1行欄。1行欄がキャレットから最も遠くなる
- キャレットの**上**に置く → キャレット → 1行欄 → 矩形。**1行欄がキャレットに隣接する**

打鍵中ユーザーの目は1行欄にあり、ホストのキャレットは「テキストが着地する場所」を示す
静止したアンカーである。この二つは近いほうがよく、テキストが下から上へ流れる動きとも一致する。
上に余裕がないときのみ、やむなく下に出す。

案 A ではキャレットとの位置関係が切れるため、この議論は成立しない。代わりに
「視線が動かないこと」自体が利点になる。**ブロック内部のレイアウトはどちらの案でも同じ**なので、
配置は後から切り替えられる。設定として両方を持ち、既定は実地の比較で決める（§4.4）。

**キー入力ガイドは配置の選択に影響する。** ビジュアライザがキャレットに追従して動くと、
参照対象として機能しない（動く鍵盤図を目で追うことになる）。案 B でビジュアライザを使うなら、
**ビジュアライザだけを固定位置に分離する**必要がある。ビジュアライザはテキストの流れの一部ではないため、
1行欄と矩形を分離する場合とは違って連続性を壊さない。

**隠す操作。**

- **ホットキー押しっぱなしで表示のみ消す**（バッファは生きたまま。離すと戻る）。
  デフォルトは Space 長押し、**設定可能**とする
- **ポインタホバーで半透明化** — キーを一つも消費しない。直感的で、ユーザーが発見できる程度に自然。
  キーバインドが衝突して使えない場合の保険にもなる

**タイマーによる自動半透明・自動折りたたみは採用しない。**
「思考のために止まった」と「書き終わった」を区別できず、日本語を書いていれば数秒の停止は頻繁に起きる。
そのたびに UI が変化すると、常時表示より不快な視覚ノイズになる。
状態変化はユーザーが原因を説明できるものだけにする。

**ホストアプリの本文は読み取らない。** ブロックが隠す領域を補うために本文を取り込む案は採らない。
見たいものには他者の書いたもの（SNS の相手の発言など）が含まれ、それは自分の持ち物ではない。
技術的可否以前の線として引く。

**新配列との衝突。** 新配列使用者はほぼ全てのキーに意味を割り当てているため、
衝突しないデフォルトは原理的に存在しない。設定可能にするのが唯一の解である。
幸い `hechima-keymap` の `analyzeKeymap()` が配列 JSON から特徴を機械的に読み出せるので、
**読み込んだ配列定義から空きキーを提案する**ことができる。

### 2.7 任意要素: キー入力ガイド

1行欄の下に、論理配列（新配列）・漢直・`gamepad-engine` のビジュアライザを置ける。
`replay-engine` 同梱のキーボード図 SVG ビジュアライザ（物理配置プロファイル＋押下ハイライト＋
手指オーバーレイ）を流用する。新配列の習得期には実質的な価値がある。
画面占有が増えるため既定はオフ。

## 3. エンジン側の要件

### `hechima-wasm` に N-best 経路 API を追加する

現状の「かな → 文節/候補 JSON」では、**区切り違いを含む経路単位の候補**が表現できない。
この UI の中核が成立しないため、ここが唯一の下層改修となる。

必要な出力（経路ごと）:

- 区切り位置の列
- 各文節の表記（および読み）
- **経路コスト**（1位との差＝マージンが取れること）

Mozc 側には既に `converter/immutable_converter_main.cc` がラティスをダンプする実装がある。
出力ヘッダは以下で、ノードごとに `wcost` / `cost` とリンク構造を持つ。

```
id  key  value  begin_pos  end_pos  lid  rid  wcost  cost  bnext  enext  prev  next
```

**ImmutableConverter は rewriter を通っていない**ことが重要である（rewriter は上位の Converter が
後から被せる層）。後述のとおり `cost` の意味が均質になるため、マージンを扱うならこの層が望ましい。

グループ化（区切りでまとめて代表経路を選ぶ）は JS 側で行う。WASM 側は経路をそのまま返す。

### 実装状況（2026-09-20）

`logical-layout-labo/hechima-wasm/hechima_wasm.cc` に `hechima_paths` を実装済み。
ネイティブ（aarch64 Linux）でビルドと自己テストまで通っている。wasm 版は CI での焼き直しが要る。

```
hechima_paths(kana, max_paths, expand)
→ {"paths":[{"base":true,"cost":17573,"sizes":[4,3,2],
             "segments":[{"key":"ここでは","value":"ここでは"},...]}, ...]}
```

**分節を揺らさない。** ラティスは 1 回組めば全ての区切りを含んでいるので、
揺らして変換し直すのは無駄な労力になる（そこまでの段階で既に分節が決まってしまっている）。

1. `ImmutableConverter::Convert(options, &segments, &lattice)` —— ラティスを受け取れる
   公開オーバーロードでラティスごと取る
2. Mozc 自身の `NBestGenerator` を **[BOS, EOS] の全域**に当てる
   （`ONLY_EDGE` + `FILL_INNER_SEGMENT_INFO` = リアルタイム変換と同じ設定）。
   1 候補 = 全文 1 経路で、内部の文節境界が載る
3. 同じ区切りの経路は初出（= その区切りの最良）だけ残して畳む

`cost` は A\* が出す**本物の経路コスト**なので、区切りの異なる経路どうしを直接比較できる。

`engine::Modules` は `Engine::GetModulesForTesting()` から借りている。
名前のとおりテスト用の口なので、上流の変更で消える可能性がある（要注視）。

**候補の一覧は返さない。** 区切りを選んだ後の候補は既存の
`hechima_convert2(kana, sizes_csv, max_cands)` で取る（`sizes` をそのまま渡せる）。
役割を分けてあり、`hechima_paths` は「どの区切りか」だけを速く決める。

#### 実測（2026-09-20 / 10 入力）

| 項目 | 結果 |
|---|---|
| base が cost 1 位 | **10 / 10** |
| 2 位とのマージン | min 103 / 中央値 880 / max 4632 |
| レイテンシ | **1〜5ms**（10〜16 文字） |

```
base  cost=17573  ここでは | 着物を | 脱ぐ
      cost=18294  ここで   | 履物を | 脱ぐ      （+721）
base  cost=23308  庭には | 庭   | 鶏が | いる
      cost=23976  庭に   | 埴輪 | 鶏が | いる    （+668）
```

マージンは素直に散っている。「すもももももももものうち」が +103（本当に曖昧）、
「かれがくるまでまつ」が +4632（自信あり）。§4 の観測量として機能しそうに見える。

> **失敗した最初の実装（記録）**
>
> 当初は公開 API だけで済ませようとして、`StartConversion` + `ResizeSegments` で分節を
> 揺らし（境界をずらす・結合・分割のビーム探索）、`Candidate::cost` の総和を経路コストの
> 代用にした。**これは使えない。** `Candidate::cost` は「その文節の部分ラティスの中での」
> コストなので、足しても経路コストにならない。実測（同じ 10 入力・各 40〜60 経路）:
>
> - 総和が最小になる経路は 10/10 で base より文節数が少ない（文節が 1 つ増えるごとに中央値 +5640）
> - base は総和の順位で 4〜31 位 / 40〜60 本。**同じ文節数に限っても** base が 1 位は 2/10
>
> レイテンシも 97ms かかっていた（ラティス版は 1ms）。
> 教訓として、**per-segment のコストを足して経路コストを名乗らせない**こと。

### 注意: Mozc の `cost` は較正された確率ではない

コストは原理的には -log 確率（単語生起コスト＋連接コストの和を Viterbi で最小化）であり、
差は対数尤度比に対応する。順位付けのためだけの順序数ではない。
しかし最終的な `cost` フィールドに入る値は、以下の理由で確率的解釈が崩れている。

- **定数のベタ書き** — 例: `rewriter/single_kanji_rewriter.cc` で単漢字候補に `cost = 5000`。
  rewriter 群には cost を直接操作する箇所が 30 以上ある
- **変換後の上書き** — `converter/candidate.h` に `cost_before_rescoring` があり、
  `engine/supplemental_model_interface.h` の `RescoreResults()` で再スコアリングされうる
- **ユーザー学習** — 履歴による順位調整も同じフィールドに乗る
- **正規化されていない** — パスコストは候補全体で正規化されていないため、
  差から比は出せても「正解である確率」は出ない
- **モデル誤設定** — n-gram が捉えられない依存については、コスト差は「自信」ではなく
  **モデルの盲点**を反映する。マージンが大きくても間違えるのはこのため

結果として、一つの整数フィールドに確率由来の値とヒューリスティック由来の値が同居している。
Mozc は**論拠（確率）と方針（これは出したい）を同じ `cost` に畳み込んでいる**ため、後から分離できない。

実務上の帰結:

- **マージンを閾値に使うなら ImmutableConverter 層で取る**（rewriter 混入がゼロ）
- 上位層のコストを使う場合は、日付・記号・単漢字・絵文字・計算結果を対象から除外する
- 閾値は理論的に決まらない。**実データで切る**（§4）

## 4. 実験計画

UI を作る前に、Mozc だけで取れる数字を先に取る。
これを飛ばすと、個別の失敗を個別の補正で潰していく作業になり、
効いているかどうかを判定する指標が永久に手に入らない。

### 4.1 評価データ

`fcitx5-mozc` に同梱のものをそのまま使える。

| ファイル | 件数 | 内容 |
|---|---|---|
| `data/dictionary_oss/evaluation.tsv` | 602 | **全文の変換結果**つき。`status / input / output / command / argument / version` |
| `data/test/quality_regression_test/oss.tsv` | 501 | 部分制約（`Conversion Match` / `Not Match`）。既知の誤変換パターンの列挙 |
| `data/test/quality_regression_test/regression.tsv` | 102 | 同上 |
| `data/test/quality_regression_test/myoji.tsv` | 50,614 | 名字専用。今回は対象外 |

`evaluation.tsv` は当時の出力スナップショットにバージョン番号が付いているため、
**現行ビルドとの差分を取るだけで回帰の有無が分かる**。最も扱いやすい。

なお Mozc の品質回帰テストは全文の正解を書かず、部分制約（含むべき／含むべきでない）で
書かれている。正解が一意に定まらない領域があるためだが、副作用として
**個別の補正がテストによって固定化され、外せなくなる**構造を生んでいる。
この評価セットを使う際は「既知の失敗の禁止リスト」であって「正解の定義」ではないことに注意する。

### 4.2 先に取る数字

**(1) 区切りの事後確率（旧「経路マージン」）**

当初は「1 位経路と 2 位経路のコスト差」を観測量にする予定だったが、**差だけでは足りない**。

まず前提として、**コストは対数領域の量なので、比ではなく差を見るのが正しい**。
差がそのまま対数尤度比になる。絶対コストで割ってはいけない —— 絶対コストは
文長にほぼ比例するだけの量で（10 入力で字数との相関 0.635、1 字あたり約 1700）、
割ると長い文のマージンが不当に小さく見える。

問題は別のところにある。**対抗馬は 1 本とは限らない。**

| 読み | Δ2位 | 区切り数 | P(base) λ=500 |
|---|---|---|---|
| ここではきものをぬぐ | 721 | 9 | 0.803 |
| にわにはにわにわとりがいる | 668 | 11 | 0.674 |
| あのひとはいしゃだ | 880 | 12 | 0.814 |
| くるまではこをはこぶ | 872 | 7 | 0.849 |

生の差はほぼ同じでも、対抗馬の本数で事後確率は大きく変わる。
Δ で並べた順位と P で並べた順位は実際に入れ替わる。

なので観測量は**区切りの事後確率**にする。

```
P(区切り_i) ∝ Σ_{その区切りを持つ経路 p} exp(-cost(p) / λ)
```

分布の集中度を見る形で、これは Jev の Choice の confidence と同じ量である。

**Σ を取る（周辺化する）ことが要る。** ある区切りの尤もらしさは、その区切りを持つ経路
すべての確率の和であって、最良 1 本ではない。実測では最良 1 本だけを使う場合と比べて
P(base) が最大 ±0.14 動いた（「すもももももももものうち」+0.117 /「このみかんはおいしい」-0.138）。
`hechima_paths` は `npaths` と `costs`（その区切りを持つ経路のコスト列、最大 32 本）を
返すので、ホスト側で任意の λ で計算できる。

**λ（コスト → 対数確率のスケール）は未較正。** これがこの実験の唯一の自由パラメータになる。
λ は実質「対抗馬の本数をどれだけ重く見るか」のつまみで、λ→0 で「マージンだけ」、
λ→∞ で「区切りの本数だけ」に漸近する。評価セットで正解率に対して較正する。

**(2) マージン別の正解率（信頼性図）**
マージンを分位で切り、各ビンでの正解率をプロットする。
**この図がこの実験の成否を決める。**

- **単調に上がる** → コスト差には情報がある。マージンをゲートとして使えるし、閾値を切る意味がある
- **寝ている** → 実質的に順位付けだけの量。マージンゲートという設計そのものが崩れる

**(3) マージン小の部分集合における正解率**
上積みの余地を直接示す数字。

- **50% 近い** → コイン投げ状態。Mozc のコストがそこで情報を失っている。理想的な標的
- **80% ある** → マージンが小さくても Mozc は当てている。抜くのは難しい

**(4) 区切りで割れている頻度**
N-best 経路の上位が区切りで食い違うケースの割合。
これがこの UI の中核機能が働く頻度そのものになる。

**(5) 誤りの内訳**
1位経路と正解経路の差分を「区切りが違う / 単語が違う / 両方 / 未知語」で分類する。
文節ごとに正誤を数えるのは Mozc の構造（経路探索）に合っていない。

未知語は**候補に存在しない語**であり、この UI では原理的に救えない
（カバレッジのボトルネックは辞書側にある）。内訳から除外して考える。

### 4.2b 測定結果（2026-09-20・第 1 回）

`data/dictionary_oss/evaluation.tsv` のうち `Conversion Expected*` の **509 件**（`argument`
= 正解の全文変換）に対して `hechima_paths`（`max_paths=60 / expand=800`）を流した。
gold の分節は既存の `hechima_split` で取得。全 509 件が 0.77 秒（init 込み・**約 1.4ms/件**）。

> ⚠ これは**既知の難例を集めた回帰セット**であり、通常の文の分布ではない。
> 記録時点の Mozc 自身も 169/601 件が FAILED になっている。絶対値ではなく内訳を見ること。
> また `hechima_paths` は rewriter を通らない ImmutableConverter 層なので、
> 製品の変換より弱く出る。

**誤りの内訳（§4.2 (5)）**

| 分類 | 件数 | 割合 |
|---|---|---|
| A. base がそのまま正解 | 261 | 51.3% |
| B. **別経路が正解**（経路選択で救える） | 27 | **5.3%** |
| C1. 区切りは合っているが語が違う | 129 | 25.3% |
| C2. 正しい区切りは列挙済み・語が違う | 34 | 6.7% |
| C3. 正しい区切りが列挙に無い | 58 | 11.4% |

**この UI の天井は B の 5.3 ポイント。** C1+C2 の 32.0% は区切りではなく**候補選択**の問題で、
`hechima_convert2` の領分（区切りを選んだ後の話）。C3 の 11.4% は経路の打ち切りではなく
（該当ケースの経路数は 2〜9 本で上限 60 に遠い）、必要な語がラティスに出ていない
= 辞書カバレッジの問題。§6 の非目標どおりこの層では解けない。

**区切りで割れている頻度（§4.2 (4)）**: 501 / 509 件で 2 つ以上の区切りが列挙される。
つまり「割れているか否か」は頻度では絞れない。**事後確率で絞る必要がある。**

**マークのゲート性能（§4.2 (2)(3) / §4.5）**

P(base) < しきい値 でマークしたときの性能（λ=500）:

| しきい値 | マーク率 | 救えるケースの捕捉率 | マークの適合率 |
|---|---|---|---|
| 0.7 | 11.8% | 70.4% | 75.0% |
| **0.9** | **21.8%** | **88.9%** | **64.9%** |
| 0.99 | 40.7% | 96.3% | 55.1% |
| （全件マーク） | 100% | 100% | 48.7% |

**P(base) < 0.9 で、5 文に 1 文をマークして救えるケースの 9 割を捕捉できる。**
校正ツールのゲートとしては十分に使える水準。

**P(base) が何を測っているか（重要）**

較正と識別力を分けて測ると、この量の性格がはっきりする（λ=500）。

*較正*: まったく合っていない。

| P(base) | 実際の正解率 | 件数 |
|---|---|---|
| 0.000–0.500 | 42.1% | 19 |
| 0.500–0.900 | 33.7% | 92 |
| 0.900–0.990 | 56.2% | 96 |
| 0.990–0.999 | 53.7% | 108 |
| 0.999–1.000 | **56.7%** | 194 |

P(base)≈1.0 でも実際の正解率は 57%。下 2 段は単調ですらない。

*識別力（AUC）*:

| 何を予測するか | λ=500 | λ=1000 |
|---|---|---|
| base が正解か | **0.585** | 0.557 |
| 救えるケースか（base 誤り かつ 別経路に正解） | **0.878** | 0.798 |

**base の正誤に対してはほぼコイン投げ（0.585）。** P(base) は「Mozc のモデルの下で
分節の事後確率がどれだけ集中しているか」であって、「モデルが正しいか」ではない。
この 2 つがずれるのは**モデルが自信満々に間違えるとき**で、n-gram が捉えられない
依存についてはコスト差が自信ではなくモデルの盲点を反映する（§3「`cost` は較正された
確率ではない」と同じ話）。

一方、モデルが迷っているときは対抗馬の中に正解が混じっている確率が高い。だから
「正解が近くにあるか」には 0.878 で効く。**このゲートは「base は誤り」ではなく
「正解があるとすれば近くにある」と言っている。**

実務上の線引き:

- ○ 「下位 20% をマークする」（予算配分の判断）
- ○ 「P<0.9 なら代替を出す」（代替を出す価値があるかの判断）
- ✗ 「P=0.95 だから安全、マークしない」（実際の正解率は 57%）
- ✗ Jev の分布と足すとき両方が較正済みと仮定する（§5。λ はスケール換算だけでなく
  **較正のずれも吸収する**必要がある = 理論的には決まらない）

較正は等調回帰などで直せるが、**較正では識別力は上がらない**。AUC 0.585 は
「その程度の情報しか入っていない」という意味で、較正しても数字が誠実になるだけで
情報は増えない。

### 4.2c 効き目の本体は区切りではなく候補選択だった（2026-09-20）

C1/C2/C3（base が誤りで、別経路にも正解が無い）221 件について、**gold の区切りを与えて**
`hechima_convert2` を回し、各文節の正解表記が候補リストに入っているかを見た。

| 正解が候補に無い文節がある | 17 | 8.9% |
| 分節を再現できず | 26 | 13.5% |

正解候補の順位は中央値 2 位・最大 24 位で、リランカーの射程内。

**救える余地の比較（全 509 件に対して）**

| | 上積み |
|---|---|
| 経路選択（区切りを選び直す） | **5.3 ポイント** |
| 候補選択（区切りは正しく、語が違う） | **26.7 ポイント** |

**5 倍の開きがある。** 精度を取りに行くなら梃子は候補選択の側にある。

この事実は §1 の動機を揺るがさない。この UI の正当化は「現在の UI が構造的に
区切り違いを表現できない」ことであって「精度が大きく上がる」ではなく、
5.3 ポイントは最初から見えていた天井である。**目的の違う 2 つの梃子として分けて扱う。**

- **経路選択** = UI の穴を埋める（現在の IME では救えないものを救う）

## 5. 将来の拡張点

### 文をまたぐ判断は Mozc には原理的にできない

Mozc の変換単位は実質 1 文で、Viterbi も文内で閉じている。
したがって 3 文バッファを持っても、**Mozc だけでは 3 文分の文脈を精度に使えない**。

3 文保持の根拠は現状こうなっている。

- (a) 文脈を使って精度を上げる … **Mozc では満たせない（空席）**
- (b) ユーザーが 3 文を見渡して校正できる … 成立
- (c) FIFO を滑らかに回す … 成立

(b)(c) だけで 3 文保持は正当化されるが、(a) は空いたままである。

### 空席の埋め方（現時点では実装しない）

文全体・複数文を見た上での判断を外部モデルに委ねる余地がある。
標的を絞るなら **「1位経路と2位経路が区切りで食い違い、かつコスト差が小さいケース」**
が最も条件が揃う。選択肢の重なりが小さく、体感インパクトが大きく、現在の UI では救えない領域である。

ただし現時点では**実装しない**。理由:

- オフラインで動くこと（IME としては大きい）
- レイテンシがゼロであること
- UI と測定を先に済ませ、Mozc のマージンだけで実用になるかを見てから判断できること

外部モデルを使う場合の設計上の注意（先に書いておく）:

- **各文節を独立に選ぶと、全体として破綻した系列が出る**（marginal argmax ≠ joint argmax）。
  経路単位で選ばせるか、分布を Mozc のコストと合成して Viterbi を回す
- **候補にない語は選べない**。カバレッジは常に辞書側の問題として残る
- **選択肢の重なりが大きいと分布が割れる**。表記ゆれを選ばせてはいけない
- **出力は論拠であって結論ではない**。合成（重み・閾値）はコード側に明示的に置き、
  生の判断は再利用可能なまま保つ。Mozc の `cost` が陥っている状態を繰り返さない

## 6. 非目標

- **表記ゆれの自動選択** — 許容する。必要ならユーザー設定で決め打ち
- **OS 全体での動作** — まず `site` 上で実装する。
  preedit を使わず確定文字列だけを commit する構成なので OS 上にも乗りうるが、後で考える
- **大規模な校正** — エディタの役割。このツールは直近 3 文の微視的な校正に限る
- **未知語・固有名詞の救済** — 辞書のカバレッジの問題であり、この層では解けない
